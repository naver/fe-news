## [Tailwind Labs is joining Shopify](https://tailwindcss.com/blog/tailwind-is-joining-shopify)

<img src="https://tailwindcss.com/_next/static/media/og-image.103kpqahmns2b.jpg" width=500>

Tailwind CSS를 만든 Adam Wathan이 2026년 9월 9일 Tailwind Labs가 Shopify에 합류한다고 발표했다. Tailwind CSS는 주당 1억 1천만 회 넘게 설치되고 ChatGPT, X, Cloudflare, Reddit 등이 쓰는 CSS 프레임워크이며, Shopify는 Tailwind를 일찍 도입한 대규모 기업 중 하나다.

Tailwind CSS를 비롯한 오픈소스 프로젝트는 계속 MIT 라이선스로 남고, Tailwind 팀이 Shopify의 지원을 받아 유지보수를 이어 간다. Tailwind CSS를 이미 쓰고 있는 팀이 당장 바꿀 것은 없다. 대신 Tailwind Labs는 Tailwind를 중심으로 한 유료 사업을 더 키우지 않는다. 유료 UI 컴포넌트·템플릿 모음 [Tailwind Plus](https://tailwindcss.com/plus)와 UI 작업용 에이전트 스킬 모음 [ui.sh](https://ui.sh/)는 신규 가입을 받지 않고, 기존 고객만 계속 쓸 수 있다.

Wathan은 사용자와 같은 문제를 겪는 실제 제품 안에서 프레임워크를 개발하고 싶었고, 판매자 스토어프런트와 관리 도구, 결제, Shop 앱, AI 에이전트가 대신 구매하는 에이전틱 커머스(agentic commerce)까지 다루는 Shopify가 그런 환경이라고 설명한다.

## [Deno is joining Cloudflare](https://deno.com/blog/cloudflare)

Node.js와 Deno를 만든 Ryan Dahl이 2026년 10월 9일 Deno 팀 전원이 Cloudflare에 합류한다고 발표했다. 별도 런타임과 호스팅 서비스를 계속 개발하는 대신, [Cloudflare Workers](https://workers.cloudflare.com/), [Durable Objects](https://developers.cloudflare.com/durable-objects/) 팀과 함께 하나의 플랫폼에 개발 역량을 모으기로 했다고 설명한다.

발표에 따른 서비스별 변경 사항은 네 가지다.

- **Deno 런타임**: 앞으로 1년간 버그 수정과 보안 업데이트를 담은 월간 릴리스를 내고, 그 뒤 개발을 종료한다. 코드는 오픈소스로 남고, 팀은 개발을 이어 갈 사람을 환영한다고 밝혔다.
- **Deno Deploy**: 6개월간 운영한 뒤 서비스를 종료한다. 유료 고객이 Cloudflare Workers로 옮길 수 있도록 마이그레이션을 지원한다.
- **[JSR](https://jsr.io/)**: Deno 팀이 만든 JavaScript·TypeScript 패키지 레지스트리로, 계속 운영하며 인프라를 Cloudflare로 옮긴다.
- **[rusty_v8](https://github.com/denoland/rusty_v8)**: V8 엔진의 Rust 바인딩으로, 계속 지원하며 Workers 런타임인 [workerd](https://github.com/cloudflare/workerd)에 통합하는 작업을 진행한다.

Ryan Dahl은 Deno와 Deno Deploy에 이어 Workers 프로그래밍 모델 기반의 분산 애플리케이션 플랫폼 [celld](https://celld.dev)를 만들어 온 흐름이 이번 결정의 배경이라고 설명한다. 저렴한 서버리스 실행과 영속 상태, WebSocket을 함께 제공하는 Durable Objects가 에이전트 하네스(모델 호출과 도구 실행을 관리하며 에이전트를 돌리는 실행 환경)에 잘 맞는다고도 본다. [Cloudflare 블로그 글](https://blog.cloudflare.com/deno-joins-cloudflare)에 따르면 celld는 workerd와 합쳐지고, Ryan Dahl과 Deno 공동 창업자 Bert Belder가 workerd 자체 호스팅을 정식 지원하는 작업을 이끈다.

Deno 런타임이나 Deno Deploy로 서비스를 운영하고 있다면 발표일(10월 9일)을 기준으로 한 지원 종료 일정에 맞춰 마이그레이션 계획을 세워 둬야 한다.

## [The AI cost of JavaScript frameworks](https://nolanlawson.com/2026/10/28/the-ai-cost-of-javascript-frameworks/)

<img src="https://nolanlawson.com/_astro/frameworks.B14_z7MF_2lv3q1.webp" width=500>

코딩 에이전트가 만드는 코드의 비용과 품질이 프레임워크에 따라 달라지는지 [Nolan Lawson](https://nolanlawson.com/)이 직접 측정한 글이다. "에이전트에 더 잘 맞는 프레임워크" 같은 주장을 감이 아니라 근거로 따져 보자는 취지다.

실험에서는 PokéAPI로 검색과 필터를 갖춘 작은 포켓몬 앱을 만들게 하고, 접근성 트리 기반의 적합성 테스트와, 있는 경우 프레임워크의 공식 MCP나 스킬을 함께 줬다. Angular, Astro, Next.js, Nuxt, Qwik, React Router, SolidStart, SvelteKit, TanStack Start, Hono+htmx, Gracile+Lit, Vanilla(Vite) 12개 구성을 Claude Opus 5.5(high effort)로 5회씩 실행해 중앙값을 냈다(Angular는 두 번 실패해 유효한 3회 결과만 썼다). Claude Code가 산정한 API 요금 기준으로 비용은 Hono+htmx가 2.67달러로 가장 적고 Astro가 2.76달러로 뒤를 이었으며, Angular가 4.97달러로 가장 많았다. 토큰은 Nuxt(385만)가 가장 적고 Angular(976만)가 가장 많았으며, 홈 화면에서 전송한 JavaScript는 Astro 0KiB, Next.js 142KiB로 차이가 컸다. Lighthouse 점수는 접근성이 모두 100점, 성능이 97\~100점으로 거의 차이가 없었다.

저자는 앱이 작고 콘텐츠 중심이라는 점, 실행마다 결과가 달라진다는 점, 에이전트가 프레임워크의 MCP나 스킬을 일관되게 쓰지 않았다는 점을 한계로 밝힌다. 승자를 가리기보다 에이전트가 짠 코드도 근거를 두고 비교할 수 있음을 보여 주려 했다며, [벤치마크 저장소](https://github.com/nolanlawson/agent-framework-benchmark)를 포크해 직접 다시 돌려 보라고 권한다.

## [Ship less JavaScript in Next.js with your AI agent](https://nextjs.org/blog/ship-less-javascript-with-ai)

<img src="https://h8dxkfmaphn8o0p3.public.blob.vercel-storage.com/static/blog/ship-less-javascript-with-ai/twitter-card.png" width=500>

Next.js 16.4와 함께 나온 번들 최적화 에이전트 스킬 [`next-bundle-optimizer`](https://www.skills.sh/vercel/next.js/next-bundle-optimizer)를 소개하는 글이다. Vercel은 이 스킬로 AI 앱 빌더 [v0](https://v0.app/)와 vercel.com에서 압축 기준 2MB 가까운 불필요한 JavaScript를 덜어 냈다고 밝혔다. v0에서는 실험 중인 코드 에디터가 실험군이 아닌 사용자에게도 먼저 로드되던 문제를 찾아 대부분의 페이지에서 150KB를 줄였다.

```bash
npx skills add vercel/next.js --skill next-bundle-optimizer
```

`React.lazy()`로 미뤄 둔 컴포넌트도 같은 번들의 다른 모듈이 정적으로 import하면 처음부터 로드된다. 스킬은 이런 숨은 import 관계를 찾도록 에이전트에 Turbopack 모듈 그래프를 열어 준다. 에이전트는 Bundle Analyzer(`next analyze`)의 스냅숏을 JSON으로 내보내 모듈·청크 그래프를 재구성하고, 서로 연결된 큰 모듈 묶음을 찾은 뒤 [최소 절단(minimum cut)](https://en.wikipedia.org/wiki/Minimum_cut)으로 적은 수의 import 경계만 바꿔 로딩을 미룰 방법을 제안한다.

Server Components로 옮길 수 있는 로직, 중복된 대형 의존성, 트리 셰이킹이 적용되지 않은 코드도 찾으며, `/next-bundle-optimizer fix`로 수정을 적용한 뒤 다시 분석해 효과를 비교한다. 사람이 직접 쓰는 Bundle Analyzer에도 큰 라우트 요약, 크기순 테이블, 스냅숏 비교, 초기 렌더링 경로 필터가 추가되어, 번들이 커진 원인을 찾을 때 에이전트에 맡길 일과 직접 확인할 일을 나눌 수 있다.

## [How Notion handles concurrent editing with CRDTs](https://www.notion.com/blog/how-notion-handles-concurrent-editing-with-crdts)

<img src="https://images.ctfassets.net/spoqsaf9291f/7poBA7DbIwyzEkIf7UGT2C/ac91ef880b3e933e2fbc2dfe499dca45/Hands_on_solid_color.png" width=500>

Notion 팀이 동시 편집 시스템을 [CRDT(Conflict-free Replicated Data Type)](https://en.wikipedia.org/wiki/Conflict-free_replicated_data_type)로 바꾼 과정을 설명한 글이다. 이전에는 블록 단위 레코드를 마지막 쓰기가 이기는(last-write-wins) 방식으로 처리해, 두 사람이 같은 블록을 동시에 고치면 한쪽 변경이 사라졌다. 오프라인 모드를 도입하면 이 위험이 더 커지기 때문에, 팀은 2025년 7월 CRDT 기반 시스템을 프로덕션에 배포했다.

텍스트는 RGA(Replicated Growable Array) 계열의 시퀀스 CRDT로 다룬다. 지금까지 입력된 모든 글자를 트리의 노드로 두고, 세션 ID와 [램포트 시계(Lamport clock)](https://en.wikipedia.org/wiki/Lamport_timestamp)를 합친 ID로 순서를 정한다. 사용자가 지운 글자도 데이터에서 없애지 않고 삭제 표시(tombstone)만 남겨, 늦게 도착한 연산도 위치를 찾게 한다. 굵게, 링크 같은 서식은 [Peritext](https://www.inkandswitch.com/peritext/) 알고리즘을 바탕으로 처리해, 굵은 글씨 끝에서 입력하면 굵게 이어지고 링크 끝에서는 이어지지 않는다.

Notion에서 특히 어려운 부분은 블록 분할이다. 블록 중간에서 Enter를 누르면 새 블록이 생기는데, 이때 동시에 들어온 편집이 맞는 블록에 들어가야 한다. 팀은 블록 안의 글자 묶음을 슬라이스로 관리해 분할할 때 슬라이스 일부를 새 블록으로 옮기고, 분할할 때마다 `L`이나 `R`을 덧붙이는 검색 레이블로 동시에 들어온 편집이 나뉜 블록 중 어디에 속하는지 찾게 했다. Yjs 기반 ProseMirror 에디터에서는 블록을 나누는 동안 들어온 편집이 원래 노드에 남을 수 있다. 저자는 이와 비교해 Notion의 방식이 다른 에디터에도 쓸모 있으리라고 보지만, 아직 검증하지는 않았다고 밝힌다.

Notion은 현재 분당 수백만 건의 CRDT 연산을 처리하며, 검색 레이블을 압축 인코딩해 저장 효율을 다섯 배 높였다. 블록 분할과 병합이 있는 에디터에 협업 기능을 붙인다면, 쓰는 CRDT 라이브러리가 분할 중에 들어온 편집을 어디로 보내는지부터 확인해 볼 만하다.

## [JPEG XL vs AVIF for web use-cases](https://jakearchibald.com/2026/jpeg-xl-vs-avif/)

<img src="https://jakearchibald.com/c/img-B1T1kkPz.jpg" width=500>

JPEG XL이 모든 주요 브라우저에 들어오면서, [Jake Archibald](https://jakearchibald.com/)가 웹에서 AVIF와 JPEG XL 중 무엇을 써야 하는지 직접 인코딩해 비교했다. avifenc, libjxl(cjxl), 새 JPEG XL 인코더인 [jixel](https://github.com/awxkee/jixel)로 사진, 스크린샷, 일러스트, 투명 이미지, HDR 이미지를 인코딩하고, 사람이 느끼는 화질 차이를 수치로 나타내는 지표인 [SSIMULACRA2](https://github.com/cloudinary/ssimulacra2)와 [ColorVideoVDP](https://github.com/gfxdisp/colorvideovdp)로 화질을 맞춘 뒤 파일 크기와 디코딩 시간을 쟀다.

손실 압축에서는 AVIF가 앞섰다. 기본 인코딩 강도에서 JPEG XL은 사진에서 15\~25%, 스크린샷과 일러스트에서 30\~90% 더 컸고, 디코딩도 중간 화질 기준 2\~3배 오래 걸렸다. 무손실 압축에서는 반대로 JPEG XL이 앞서, AVIF가 30\~120% 더 컸다. 기존 JPEG을 손실 없이 JPEG XL로 바꾸면 9\~20%를 줄일 수 있고, libjxl로 인코딩하면 점진적(progressive) 렌더링을 거의 추가 비용 없이 쓸 수 있다(jixel은 기본 강도에서 점진적 렌더링을 쓰면 파일이 12% 커진다). 다만 점진적 미리보기는 Firefox와 Chrome에서만 보이고 Safari는 최종 이미지만 그린다.

저자는 기본 선택으로 색 정보를 줄이지 않는([크로마 서브샘플링](https://en.wikipedia.org/wiki/Chroma_subsampling)을 하지 않는) AVIF 4:4:4를 감당할 수 있는 가장 높은 인코딩 강도로 쓰고, 파일이 유난히 크면 jixel로 JPEG XL을 시도하며, 무손실 이미지는 JPEG XL로 만들라고 권한다. 움직이는 이미지는 이미지 포맷 대신 비디오로 만들고, AVIF 4:2:0은 기본값으로 쓰지 말라고 덧붙인다. 결과가 이미지마다 다르니 서비스에서 쓰는 이미지로 직접 시험해 보라고 강조한다.

## [Styling Linear for the future with StyleX](https://linear.app/now/styling-linear-for-the-future-stylex)

<img src="https://webassets.linear.app/images/ornj730p/production/6bd409a259a2f36edf91b977d0963be84542b521-2400x1350.png?q=95&auto=format&dpr=2" width=500>

[Linear](https://linear.app/)의 Kenneth Skovhus가 React 앱의 스타일링을 styled-components에서 Meta의 CSS-in-JS 라이브러리 [StyleX](https://stylexjs.com/)로 옮긴 과정을 정리했다. styled-components는 렌더링 중에 스타일을 만들어 CSS 규칙을 주입하는 비용이 있었고, React 18로 올린 뒤 성능이 떨어졌으며, 유지보수 모드에 들어갔다. `styled(Button)`처럼 컴포넌트 바깥에서 스타일을 덮어쓰기 쉬워 회귀를 추적하기 어려웠고, 에이전트가 그럴듯해 보이지만 틀린 코드를 내놓기도 쉬웠다.

StyleX는 빌드 시점에 스타일을 만들고, 바깥에서 스타일을 덮어쓰기 어렵게 만들며, 선택자 명시도(specificity)와 상관없이 예측할 수 있게 스타일을 합친다. 다만 속성 단위 병합이 기본 스타일을 조용히 지울 수 있어, 팀은 자체 타입 기반 검사기로 이 동작을 추적했다. 팀은 변수, 상수, 공통 프리미티브로 기반을 정한 뒤 에이전트의 도움을 받아 결정적(deterministic) 코드모드 [styled-components-to-stylex-codemod](https://github.com/skovhus/styled-components-to-stylex-codemod)를 만들어 공개했고, 다른 컴포넌트를 감싸지 않는 말단 컴포넌트부터 옮겼다. 남은 styled-components 수를 보여 주는 개발 도구, 진행률 그래프, 새 styled-components가 들어온 PR을 알려 주는 봇으로 진행 상황을 관리하고, 작성 실수나 디자인 토큰 사용은 Oxlint 규칙으로 검사했다. 전환은 1,000개가 넘는 PR로 끝냈다.

렌더링하는 컴포넌트가 많은 페이지에서는 런타임 스타일 주입이 사라지며 메인 스레드 CPU 작업이 약 20\~35% 줄었고, 내비게이션 중 주입되던 수백 개의 CSS 규칙이 0개가 되었다. 에이전트에는 좁은 범위만 맡겼고, 시각적 차이는 프로젝트 중반 새 AI 모델(Fable, Sol)이 나오기 전까지 사람이 직접 확인하는 일이 많았다. 저자는 지금 시작한다면 이 모델들에 더 많이 맡기겠다고 덧붙인다. 공개된 코드모드와 함께, 대규모 스타일 마이그레이션을 계획하는 팀이 참고할 만한 진행 방식이다.

## [Introducing tsrs: a Port of TypeScript to Rust](https://blog.cloudflare.com/typescript-rust-port)

<img src="https://blog.cloudflare.com/_emdash/api/media/file/01M5C82XAYSWX571T82A8AZRKS.png" width=500>

Go로 다시 작성한 TypeScript 7(typescript-go)이 나온 뒤, TypeScript 컴파일러를 다른 언어나 런타임으로 옮긴 구현이 연달아 공개되었다. 그중 tsrs는 Cloudflare와 [VoidZero](https://voidzero.dev/)가 Owner.com의 Max Schwenk와 함께 개발하는 Rust 포팅으로, [Oxc](https://oxc.rs/) 툴체인 안에서 인큐베이팅된다. 포크가 아니며 언어 설계는 TypeScript 팀이 계속 맡는다.

Rust를 고른 이유는 두 가지다. Go를 WebAssembly로 컴파일하면 Go의 가비지 컬렉터까지 번들해야 하지만, Rust로는 WebAssembly 게스트와 호스트가 메모리를 더 직접 주고받을 수 있다. 또 메모리 사용량이 작아 Cloudflare 샌드박스에서도 개발 도구 체인을 통째로 돌릴 수 있고, WebAssembly로 브라우저나 임베디드 기기에서도 실행할 수 있다. 팀의 초기 벤치마크에 따르면 타입 검사 워커 수가 같을 때 TypeScript 7.0보다 최대 8배 빠르고 메모리를 약 70% 덜 쓴다.

비슷한 시기에 나온 구현은 세 가지가 더 있다.

- **[ts-rust](https://github.com/pingdotgg/ts-rust)**: pingdotgg(Theo Browne)가 공개한 TypeScript 7 컴파일러의 실험적 Rust 포팅이다. Claude Opus 5.5로 약 10시간 만에 동작하는 첫 버전을 만들었고, README에 따르면 컴파일러 테스트 13,728개 설정에서 진단 결과가 TypeScript 7과 모두 일치한다. Cloudflare는 tsrs와 ts-rust를 하나의 패키지로 합치는 작업을 함께 진행한다고 밝혔다.
- **[bun check](https://bun.sh/blog/bun-v1.4.3#bun-check-a-typescript-type-checker-built-into-bun)**: Bun v1.4.3에 들어간 타입 검사기로, TypeScript 7을 포팅해 모든 CPU 코어를 쓴다. JavaScript나 `.d.ts`를 내보내지 않고 언어 서버도 없지만, `tsconfig.json`을 읽고 `typescript` 패키지 없이 동작한다. Bun이 측정한 결과로는 TypeScript 7.0.2의 `tsc`보다 3\~6.4배 빠르다.
- **[tsc-ts](https://tsc-ts.dev/)**: Vercel Labs가 TypeScript 7.0.2를 다시 TypeScript로 포팅하고 [scriptc](https://scriptc.dev/)로 네이티브 실행 파일을 만든 실험 프로젝트다. `tsc --api`와 같은 API 서버도 제공한다.

```bash
npx tsrs                               # tsrs
npx tsc-rs -p tsconfig.json            # ts-rust
bun check                              # Bun
npx tsc-ts -p tsconfig.json --noEmit   # tsc-ts
```

tsrs, ts-rust, tsc-ts는 실험 단계이고 bun check도 막 추가된 기능이며, 성능 수치는 모두 각 프로젝트가 직접 측정한 값이다. CI에서 타입 검사가 병목인 팀이라면 같은 프로젝트에서 `tsc`와 진단 결과가 같은지 비교하며 시험해 볼 수 있다.

> [참고] Go로 작성된 TypeScript 7.0은 [2026-07 소식](https://github.com/naver/fe-news/blob/master/issues/2026-07.md)에서 [TypeScript 7.0 RC](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0-rc)로 소개한 바 있다.

## [New in Chrome 154: iframes that automatically resize themselves to their content](https://www.bram.us/2026/09/23/responsive-iframes/)

<img src="https://www.bram.us/wordpress/wp-content/uploads/2026/09/responsive-iframes.png" width=500>

Chrome 154부터 `<iframe>`이 안에 담긴 문서의 크기에 맞춰 스스로 높이나 너비를 조절할 수 있다. 댓글 위젯이나 소셜 미디어 임베드처럼 콘텐츠 길이를 미리 알 수 없는 경우에 쓰기 좋다. Chrome DevRel 엔지니어 [Bramus](https://www.bram.us/)가 사용법을 정리했다.

이 기능은 양쪽이 모두 동의해야 동작한다. 임베드하는 페이지는 iframe에 `frame-sizing` CSS 속성을 지정하고, 임베드되는 문서는 `responsive-embedded-sizing` 메타 태그로 자기 크기를 전달받을 출처를 지정한다.

```css
/* 임베드하는 페이지 */
iframe {
  frame-sizing: content-height;
  width: 100%;
}
```

```html
<!-- iframe 안 문서의 <head> -->
<meta name="responsive-embedded-sizing" content="allow-origins=*">
```

문서는 로드가 끝나면 크기를 알리고, 이후 내용이 바뀌면 `window.requestResize()`를 호출해 다시 알린다. 지금까지 iframe 안팎에서 `postMessage`로 높이를 주고받던 스크립트를 CSS와 메타 태그로 대신할 수 있다. Firefox와 Safari는 아직 지원하지 않으므로 기존 방식을 대체 수단으로 남겨 둬야 한다. Chrome 팀의 설명은 [Responsive iframes in Chrome 154](https://developer.chrome.com/blog/responsive-iframes)에서 볼 수 있다.

## [Enhance multitasking extensions with the new Tabs Split View API](https://developer.chrome.com/blog/split-view-api-extensions)

<img src="https://developer.chrome.com/static/blog/split-view-api-extensions/images/thumbnail.png" width=500>

Chrome 145(2026년 2월)에 도입된 Split View는 같은 창 안에서 탭 두 개를 나란히 보여 주는 기능이다. 지금까지는 사용자가 브라우저 UI로만 조작할 수 있었는데, Chrome 155부터 확장 프로그램이 Split View를 만들고 해제할 수 있는 API가 `tabs` 네임스페이스에 추가되었다. Chrome 팀은 이 API를 WebExtensions Community Group에서 Mozilla 등 다른 브라우저 벤더와 함께 설계했다. 이 API는 `manifest.json`에 별도 권한을 선언하지 않아도 쓸 수 있다.

모든 Tab 객체에는 `splitViewId` 속성이 있어, 같은 Split View에 속한 두 탭은 같은 값을 갖고 속하지 않은 탭은 `-1`을 갖는다. 새 탭을 기존 탭과 나란히 열 때는 `tabs.create()`의 `splitWithTabId` 파라미터를, 이미 열린 두 탭을 묶을 때는 `tabs.createSplit()`을, 다시 분리할 때는 `tabs.unsplit()`을 쓴다. 두 탭은 서로 인접해야 하고, 다른 Split View에 속해 있지 않아야 하며, `pinned`, `windowId`, `groupId` 상태가 같아야 한다.

```js
// 현재 창의 Split View 조회
const tabs = await browser.tabs.query({ currentWindow: true });
const splitViews = tabs.map(tab => tab.splitViewId).filter(splitViewId => splitViewId !== -1);

// 기존 탭 오른쪽에 새 탭을 열어 Split View 생성
await browser.tabs.create({splitWithTabId: existingTab.id});

// 이미 열린 두 탭으로 Split View 생성
await browser.tabs.createSplit([existingTab1.id, existingTab2.id]);
```

그동안 멀티태스킹 확장은 여러 창의 크기를 조절하거나 `<iframe>`, 사이드 패널을 이용하는 우회 방식을 써야 했다. 브라우저 기본 Split View를 직접 제어할 수 있게 되면서 비교 보기, 문서와 미리보기 나란히 보기 같은 기능을 더 단순하게 구현할 수 있다. 자세한 사양은 [chrome.tabs API 문서](https://developer.chrome.com/docs/extensions/reference/api/tabs)에서 확인할 수 있다.

## [How to be more ambitious: A tutorial for humans with models](https://felixrieseberg.com/how-to-be-more-ambitious-a-tutorial-for-humans-with-models/)

<img src="https://storage.ghost.io/c/89/e0/89e08557-681a-40be-8264-278bf46d6b25/content/images/size/w1200/2026/10/modo_de_volar_a_way_of_flying_1951.10.55-1.jpg" width=500>

Anthropic에서 Claude.ai, Cowork, Claude Code Desktop 개발을 이끌었고 Electron 공동 메인테이너이기도 한 Felix Rieseberg가 2026년 10월 13일 공개한 글이다. AI를 쓸 때 "더 야심 차게 하라"는 말은 자주 하지만 따라 하기는 어렵다며, 실제로 쓸 수 있는 프롬프트와 함께 방법을 정리했다. [X 포스트](https://x.com/felixrieseberg/status/2110023283169247623)로 소개되어 조회 수 500만 회를 넘겼다.

저자는 야심을 속도(Speed), 고도(Altitude), 깊이(Depth), 범위(Range) 네 가지로 나누고, 이미 익숙한 속도를 뺀 세 가지를 저자 자신의 경험과 분기 사업 리뷰(QBR) 자료를 만드는 예시로 설명한다.

- **고도**: 개별 작업이 아니라 그 너머의 결과를 맡긴다. 저자는 크래시를 하나씩 고쳐 달라고 하던 방식에서 앱을 크래시 없이 유지해 달라고 요청하는 방식으로 바꿨고, 이를 위해 크래시 리포트 조회, 앱 버전과 커밋 매핑, 세 운영체제의 재현 환경을 먼저 갖췄다.
- **깊이**: 업계 최고 전문가의 도구와 방법을 쓰게 한다. 마크다운 표 대신 데이터베이스와 통계 모델을 요구하고, 원본 데이터로 기존 가정을 검증하게 하며, 모델이 스스로 평가하게 두지 말고 외부 검증 수단을 쓰라고 권한다. 이를 위해 글에 실린 프롬프트는 최고 전문가라면 무엇을 더 할지, 어떤 원본 데이터에서 시작할지, 어떤 방법과 도구를 쓸지, 무엇으로 결과를 검증할지 네 가지에 모델이 먼저 답하게 한 뒤, 그에 맞춰 원래 프롬프트를 다시 쓰게 한다.
- **범위**: 작업을 명사가 아니라 동사로 다시 정의해 참고할 분야를 찾는다. QBR은 "자료"가 아니라 "바쁜 사람이 30분 안에 인과관계에 관한 설명을 믿고 불확실한 상황에서도 결정하게 만드는 일"이며, 이렇게 보면 분석가, 기자, 편집자, 공매도 투자자 등의 방법을 빌려 올 수 있다.

후반부에서는 [자기효능감(self-efficacy)](https://en.wikipedia.org/wiki/Self-efficacy) 개념으로, 가능하다고 믿는 범위가 결과를 제한해 왔다고 설명한다. George Dantzig가 미해결 문제인 줄 모르고 숙제로 풀어 낸 일, Roger Bannister가 1마일 4분 벽을 깬 지 46일 만에 다른 선수가 다시 기록을 깬 일이 그 예다. 글에 실린 프롬프트는 코딩 에이전트에 티켓 단위가 아니라 결과 단위로 일을 맡기려는 FE 개발자가 그대로 가져다 쓸 수 있다.

## [Understanding React internals](https://www.alexandretrotel.org/articles/understanding-react-internals)

[Alexandre Trotel](https://www.alexandretrotel.org/)이 2026년 10월 29일 공개한 React 내부 동작 가이드다. React를 "무엇을 언제 렌더링하고 무엇을 미룰지 정하는 스케줄러"로 보고, React가 무엇인지부터 서버 렌더링, 하이드레이션, 렌더 단계, 커밋 단계, 훅 순서로 따라간다.

서버 장에서는 Server Components를 `id:data` 형식의 행 스트림으로 보내는 Flight 포맷과 `<!--$?-->` 같은 주석 마커로 Suspense 경계를 교체하는 스트리밍 과정을 실제 페이로드로 보여 주고, `'use client'`가 브라우저 전용이라는 뜻이 아니라 번들러를 위한 모듈 경계라는 점을 짚는다.

마지막 장에서는 훅이 Fiber의 `memoizedState`에 호출 순서대로 연결 리스트로 저장되기 때문에 조건문 안에서 부를 수 없다는 점을 설명하고, `useState`, `useRef`, `useMemo`, `useEffect`를 각각 언제 써야 하는지 정리한다. 훅 규칙이나 `'use client'`를 외운 대로만 써 왔다면 그 이유를 이해하는 데 도움이 된다.

## [Making React Context Cheap with React Compiler](https://jjenzz.com/making-react-context-cheap/)

<img src="https://jjenzz.com/og/making-react-context-cheap.png" width=500>

Context 값이 바뀌면 그 Context를 읽는 모든 컴포넌트가 다시 렌더링된다. [jjenzz](https://jjenzz.com/)는 라디오 버튼 5,000개로 이루어진 그룹에서 하나를 클릭할 때마다 5,000개가 모두 렌더링되는 상황을 예로 들어, React Compiler로 이 비용을 줄이는 방법을 보여 준다. React에는 아직 `useContextSelector`가 없어서 이런 경우 `useSyncExternalStore` 기반 스토어를 쓰는 일이 많다.

React 문서가 권하는 방법은 바깥 컴포넌트에서 Context를 읽고 필요한 값만 `React.memo`로 감싼 자식에 넘기는 것이다. 저자는 컴포넌트를 나누지 않고 Context를 그대로 읽게 둔 채 메모이제이션을 React Compiler에 맡긴다. 모든 `Radio`가 클릭마다 다시 실행되지만, `checked`, `onSelect`, `value`가 그대로면 React Compiler가 JSX와 중간 값을 재사용한다.

```jsx
function Radio({ value }) {
  const { value: selected, onSelect } = useContext(RadioGroupContext);
  const checked = selected === value;

  // checked, onSelect, value가 같으면 React Compiler가 이전 JSX를 재사용한다
  return <input type="radio" checked={checked} onChange={() => onSelect(value)} />;
}
```

Codex가 만든 벤치마크(프로덕션 빌드, CPU 감속 없음)에서 p95 클릭 처리 시간은 `useSyncExternalStore` 스토어 19.2ms, `React.memo`로 나눈 Context 18.9ms, React Compiler를 쓴 Context 18.4ms로 비슷했다. 저자는 렌더링 횟수보다 렌더링 한 번에 드는 작업량이 사용자 체감을 좌우한다며, 렌더링을 없애기보다 싸게 만드는 데 집중하라고 권한다. React Compiler를 쓸 수 없는 프로젝트를 위해 `React.memo`와 얕은 비교를 감싼 `withContextSelector` 헬퍼도 소개한다.

## [Detect when elements overlap with CSS](https://ishadeed.com/article/css-detect-overlap/)

<img src="https://ishadeed.com/assets/css-detect-overlap/thumb.jpg" width=500>

[Ahmad Shadeed](https://ishadeed.com/)가 장식 요소와 콘텐츠 영역이 겹치는 순간을 JavaScript 없이 CSS만으로 감지하는 방법을 소개한다. 장식 요소의 위치와 크기가 유동적이어서 미디어 쿼리의 고정된 중단점으로는 겹치는 시점을 맞출 수 없었기 때문이다.

방법은 다섯 단계다.

1. [앵커 포지셔닝](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Anchor_positioning)으로 `.measure` 요소를 장식 요소와 섹션 사이에 늘여, 두 요소 사이의 간격을 이 요소의 너비로 만든다.
2. `.measure` 안에 20px짜리 가상 요소를 넣고 `overflow-x: auto`를 줘서, 간격이 20px보다 좁아지면 넘침이 생기게 한다.
3. 넘침에 [스크롤 타임라인](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/scroll-timeline)을 연결한다. 사용자가 스크롤하지 않아도 넘침이 생기는 순간 타임라인이 활성화된다.
4. `timeline-scope`로 다른 위치의 요소에서도 이 타임라인을 쓰게 하고, 애니메이션으로 커스텀 속성 `--touching`을 1로 바꾼다.
5. 커스텀 속성 값으로 조건을 거는 [스타일 컨테이너 쿼리](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_size_and_style_queries)가 이 값을 보고 장식 요소를 숨긴다.

```css
.measure {
  position: absolute;
  /* 두 요소 사이의 간격 = 이 요소의 너비 */
  left: anchor(--line right);
  right: anchor(--section left);
  /* 간격이 20px보다 좁아지면 넘침이 생겨 타임라인이 활성화된다 */
  overflow-x: auto;
  scroll-timeline: --touch x;
}

.decor {
  /* 겹치면 장식 요소를 숨긴다 */
  @container style(--touching: 1) {
    opacity: 0;
  }
}
```

스크롤 기반 애니메이션, 앵커 포지셔닝, 스타일 컨테이너 쿼리를 모두 지원하는 브라우저에서만 동작한다. 스크롤 기반 애니메이션은 앞의 Firefox 159 소식에서 다룬 대로 주요 브라우저가 모두 지원하게 되었으니 앵커 포지셔닝과 스타일 컨테이너 쿼리 지원 범위를 확인하면 된다. 저자는 모든 브라우저가 지원하지 않더라도 이 기법을 점진적 향상(progressive enhancement)으로 쓸 수 있다고 본다.

## [React 19.3](https://react.dev/blog/2026/09/09/react-19-3)

<img src="https://react.dev/images/og/blog-2026-09-09-react-19-3.png" width=500>

React 19.3이 출시되었고 Next.js 16.4에도 탑재되었다. 실험 단계였던 `<ViewTransition>`과 Fragment Refs가 안정화되었고, 컴포넌트를 서버 렌더링에서 제외하는 `browser()` API가 추가되었다. 주요 변경은 네 가지다.

- **`<ViewTransition>`**: 브라우저의 [View Transition API](https://developer.mozilla.org/en-US/docs/Web/API/View_Transition_API)로 요소의 등장, 퇴장, 갱신, 위치 이동에 애니메이션을 적용한다. `startTransition`, Suspense 경계의 콘텐츠 표시, `useDeferredValue`처럼 Transition으로 표시된 업데이트에만 동작하며, `addTransitionType()`으로 같은 상태 변화에도 원인에 따라 다른 애니메이션을 줄 수 있다. Suspense 경계를 감싸면 대체 UI가 실제 콘텐츠로 바뀌는 순간에 애니메이션을 주고, 경계 안의 이미지와 폰트도 로드되는 동안 Suspense 상태로 처리되므로 애니메이션과 로딩 순서를 맞출 수 있다.
- **Fragment Refs**: `<Fragment>`에 `ref`를 넘겨 형제 DOM 노드 묶음을 다루는 `FragmentInstance`를 얻는다. 래퍼 요소 없이 이벤트 리스너 등록, 포커스 이동, `IntersectionObserver`·`ResizeObserver` 연결을 할 수 있다.
- **`browser()`**: 조건문 안에서도 호출할 수 있는 `use(browser())`를 쓰면, 그 컴포넌트는 서버에서 렌더링되지 않고 가장 가까운 Suspense 대체 UI가 표시된다.
- **Server Components에서 Context 직접 렌더링**: `'use client'` 모듈의 Context를 Provider 래퍼 컴포넌트 없이 Server Component에서 바로 렌더링할 수 있다.

```jsx
import { ViewTransition, startTransition, useState } from 'react';

function Example() {
  const [isShowing, setIsShowing] = useState(false);

  return (
    <>
      {/* Transition으로 감싼 업데이트에서만 애니메이션이 실행된다 */}
      <button onClick={() => startTransition(() => setIsShowing((v) => !v))}>토글</button>
      {isShowing && (
        <ViewTransition>
          <Component />
        </ViewTransition>
      )}
    </>
  );
}
```

이 밖에 느린 Transition이 다른 Transition을 막지 않도록 Transition마다 따로 렌더링한다. XSS를 막기 위해 DOM에 넣는 값을 검증하는 브라우저 기능 [Trusted Types](https://developer.mozilla.org/en-US/docs/Web/API/Trusted_Types_API)도 지원해, Trusted Types 객체를 문자열로 바꾸지 않고 그대로 DOM API에 넘긴다. Strict Mode는 개발 모드의 하이드레이션 중에도 Effect를 두 번 실행하므로, 업그레이드한 뒤에는 정리(cleanup) 함수가 없는 Effect부터 점검해 둬야 한다.

## [Next.js 16.4](https://nextjs.org/blog/next-16-4)

<img src="https://h8dxkfmaphn8o0p3.public.blob.vercel-storage.com/static/blog/next-16-4/twitter-card.png" width=500>

Next.js 16.4는 `'use cache'` 지시어로 컴포넌트 트리의 일부를 캐시 대상으로 표시하는 새 프로그래밍 모델 Cache Components를 모든 앱에 권장하기 시작한 릴리스다. 이제 `create-next-app`으로 만든 새 앱은 Cache Components가 켜진 상태로 시작하며, Next.js 17에서는 기본값이 된다. Cache Components는 이전 App Router의 암묵적인 캐싱 동작을 대신한다.

이번 릴리스는 Cache Components가 이전 모델과 같은 비용과 성능을 보장하지 못하던 부분을 메운다. 라우트에 `export const ensureStatic = 'navigation'`을 선언하면 동적 컴포넌트가 섞일 때 빌드가 실패해, 블로그나 커머스 페이지가 의도치 않게 요청 시점 렌더링으로 바뀌는 것을 막는다. `await navigation()`은 캐시된 콘텐츠를 프리페치에서 빼고 실제 내비게이션 때 불러오게 한다.

```jsx
import { navigation } from 'next/cache';

async function Thread({ id }) {
  await navigation(); // 프리페치 단계에서는 여기서 멈춘다
  const thread = await getThread(id);
  // ...
}
```

에이전트 도구도 늘었다. `npx next@canary upgrade --agent=latest`는 현재 버전을 확인하고 마이그레이션 가이드, 코드모드, 검증 단계를 에이전트에 넘겨 업그레이드를 끝까지 진행하게 한다. `next dev`나 `next build` 중에 보안 업데이트가 있으면 기본으로 알려 주며, `experimental.agentUpgrade`로 알림 정책(`'latest'`, `false` 등)을 바꿀 수 있다.

모든 앱에서 Turbopack 디스크 캐시가 20\~25% 줄었고, 요청이 올 때만 서버 모듈을 갱신하는 lazy server HMR, 라우트 간 공유 런타임 청크, 프로덕션 빌드의 짧은 CSS Module 클래스 이름이 적용되었다. Bundle Analyzer 개선과 `next-bundle-optimizer` 스킬은 앞의 [Ship less JavaScript in Next.js with your AI agent](https://nextjs.org/blog/ship-less-javascript-with-ai) 소식에서 다룬다. 기존 App Router 앱이라면 [`next-cache-components-adoption`](https://www.skills.sh/vercel/next.js/next-cache-components-adoption) 스킬로 프리렌더링할 수 없는 라우트부터 찾아 Next.js 17 전환 범위를 미리 가늠해 볼 수 있다.

## [TanStack Start 1.0 is Stable](https://tanstack.com/blog/tanstack-start-1-0)

<img src="https://media.tanstack.com/blog/tanstack-start-1-0/v11-title-poster.jpg" width=500>

TanStack Router에서 출발한 풀스택 프레임워크 TanStack Start가 1.0 정식 버전이 되었다. Tanner Linsley는 1.0을 핵심 애플리케이션 모델을 바꾸지 않겠다는 약속으로 설명한다. 경로, 파라미터, 검색 파라미터, 로더 데이터, 컨텍스트까지 라우트 전반의 타입 안전성을 TanStack Router에서 이어받았다. 빌드는 Vite를 기본으로 Rsbuild도 지원하고, 배포는 자체 어댑터 대신 [Nitro](https://nitro.build/)나 호스팅별 Vite 플러그인을 쓴다.

주요 기능은 다섯 가지다.

- **Selective SSR**: 라우트마다 서버 렌더링, 데이터 로딩만 서버에서 하기, 클라이언트 렌더링 중 하나를 고른다.
- **`createServerFn`**: 로더나 이벤트 핸들러에서 호출하는 타입 안전한 서버 함수다.
- **풀스택 미들웨어**: 서버와 클라이언트 호출을 감싸며 컨텍스트 타입을 경계 너머로 이어 준다.
- **`createIsomorphicFn`**: `.server()`와 `.client()` 구현을 한곳에 두면 번들마다 다른 쪽 구현을 제거한다.
- **선택형 React Server Components**: 코어가 React에 의존하지 않도록 별도 통합으로 제공한다.

AI 앱 빌더 [Lovable](https://lovable.dev/)은 사용자가 새로 생성하는 앱을 TanStack Start로 만들고, Netlify는 자사 AI 앱 빌더의 기본 프레임워크로 채택했다. 올해 Next.js에서 옮겨 간 사례도 있다. 이벤트 기반 백그라운드 작업 플랫폼 [Inngest](https://www.inngest.com/blog/migrating-off-nextjs-tanstack-start)는 App Router의 `'use client'`, `'use server'` 지시어와 여러 겹의 캐시 API가 주는 마찰, 최소 10\~12초 걸리던 로컬 첫 페이지 로드 때문에 옮기기로 했고, 옮긴 뒤에는 첫 로드가 2\~3초를 넘는 일이 드물어졌다. 클라우드 배포 플랫폼 [Railway](https://blog.railway.com/p/moving-railways-frontend-off-nextjs)는 앱이 대부분 클라이언트에서 동작해 서버 우선 패턴의 App Router가 맞지 않았다며, 200개가 넘는 라우트를 PR 두 개로 옮겨 10분이 넘던 빌드를 2분 미만으로 줄였다.

> [참고] Lovable이 Next.js에서 TanStack Start로 옮긴 과정은 [2026-09 소식](https://github.com/naver/fe-news/blob/master/issues/2026-09.md)에서 [How We Migrated lovable.dev Away from Next.js](https://lovable.dev/blog/how-we-migrated-lovable-dev-away-from-nextjs)로 소개한 바 있다.

## [htmx 4.0.0 has been released!](https://four.htmx.org/announcements/2026-08-28-htmx-4.0.0-is-released)

HTML 속성만으로 AJAX 요청과 화면 교체를 선언하는 라이브러리 [htmx](https://htmx.org/)의 4.0.0이 2026년 8월 28일 출시되었다. 내부 요청 방식을 `XMLHttpRequest`에서 `fetch()`로 바꿨다. 가장 큰 변화는 속성 상속이다. 이제 속성은 기본으로 자식에게 상속되지 않으며, 상속하려면 `:inherited` 접미사를 붙여야 한다.

```html
<!-- htmx 2 -->
<div hx-confirm="Are you sure?">
  <button hx-delete="/item/1">Delete</button>
</div>

<!-- htmx 4 -->
<div hx-confirm:inherited="Are you sure?">
  <button hx-delete="/item/1">Delete</button>
</div>
```

이벤트 이름은 `htmx:phase:action` 형식으로 바뀌어 `htmx:beforeRequest`가 `htmx:before:request`가 되었다. 히스토리 스냅숏을 더 이상 `localStorage`에 저장하지 않으며, 뒤로 가기를 하면 페이지를 다시 받아 온다. 기존 DOM을 통째로 바꾸지 않고 달라진 부분만 맞춰 포커스와 입력 상태를 지키는 [idiomorph](https://github.com/bigskysoftware/idiomorph) 기반 morph 교체가 내장되었고, 여러 대상을 한 번에 갱신하는 `<hx-partial>` 태그가 생겼으며, SSE, WebSocket, `multipart/mixed` 스트리밍 확장이 새로 나오거나 개편되었다.

`npx htmx.org@4.0.0 upgrade-check -- ./templates`를 실행하면 템플릿에서 상속에 기대는 속성, 이름이 바뀐 속성, 이전 이벤트 이름을 찾아 준다. 업그레이드 체커는 특히 `hx-headers`에 `:inherited`를 빠뜨리면 CSRF 토큰이 자식 요소에 전달되지 않을 수 있다고 경고한다. npm의 `latest` 태그는 2027년 초까지 2.x로 유지되고 4.0은 `next` 태그로 배포된다. 지금 `npm install htmx.org`를 실행하면 2.x가 설치되므로, 4.0을 시험하려면 `htmx.org@next`로 지정해야 한다. 팀은 htmx 2도 기한 없이 지원한다고 밝혔다.

## [html](https://github.com/lukeed/html)

소스 위치 정보와 CSS 선택자를 지원하는 빠른 HTML 파서다.

[Luke Edwards](https://github.com/lukeed)가 만들었으며, 전체 트리를 구성하면서도 다른 JavaScript 파서보다 3\~6배 빠르다고 소개한다. 모든 노드가 `start`, `end` 오프셋을 갖고 파싱 결과의 `position()` 메서드로 줄과 열을 얻을 수 있으며, `stringify()`는 원본 소스를 그대로 돌려준다. 속성과 텍스트는 읽는 시점에 디코딩한다.

```bash
npm install @lukeed/html
```

```js
import { parse, stringify } from "@lukeed/html";

let doc = parse(`<head><title>Hi &amp; bye</title><link rel="canonical" href="/"></head>`);
doc.find("head > title")?.text; //=> "Hi & bye"
doc.find("link[rel=canonical]")?.getAttr("href"); //=> "/"

for (let img of doc.all("img:not([alt])")) {
  let { line, column } = doc.position(img.start);
  console.log(`${line}:${column}`, stringify(img));
}
```

읽기 전용 `@lukeed/html`(gzip 6.3kB, `entities` 포함 21.8kB)과 수정할 수 있는 `@lukeed/html/mutable`(gzip 8.8kB, `entities` 포함 24.1kB)로 나뉜다. README 벤치마크(Apple M1 Max, 실제 페이지 12개, 4.79MB)에 따르면 Node.js에서 11.5ms가 걸려 ultrahtml(39.8ms), htmlparser2(66.1ms)보다 빨랐고, parse5(203.9ms)와는 차이가 더 컸다.

트리 구조는 브라우저가 쓰는 WHATWG 파싱 규칙이 아니라 htmlparser2 방식을 따르므로 잘못된 마크업에서는 브라우저 DOM과 결과가 다를 수 있고, 선택자는 css-select를 따른다. 새니타이저가 아니므로 신뢰할 수 없는 HTML을 정제하는 용도로는 쓸 수 없다. `alt`가 없는 이미지를 찾는 린트 도구나 HTML을 다루는 빌드 플러그인을 만들 때 참고할 만한 MIT 라이선스 프로젝트다.

## [PostgreSQL internals](https://pgrun.dev/postgres-internals)

PostgreSQL 서버 내부를 등각(isometric) 3D 기계 장치처럼 그린 인터랙티브 시각화다. 운영 데이터를 마스킹한 복사본으로 에이전트, CI 작업, PR마다 일회용 PostgreSQL 데이터베이스(브랜치)를 만들어 주는 서비스 [pgrun](https://pgrun.dev) 사이트에 공개되어 있다.

화면 오른쪽 버튼으로 SELECT, UPDATE, INSERT, 순차 스캔 리포트, UPDATE 후 ROLLBACK, CHECKPOINT, VACUUM, background writer 실행, 장애와 복구 같은 시나리오를 실행하면 각 구성 요소가 차례로 움직이고, 왼쪽 아래 패널이 단계마다 무슨 일이 일어나는지 설명한다. 예를 들어 접속 요청이 오면 메인 서버 프로세스인 postmaster가 인증 후 연결마다 백엔드 프로세스를 띄우고, 쿼리는 parse, rewrite, plan, execute 단계를 거친다. 데이터를 바꾸면 공유 메모리 캐시(shared buffers)의 페이지를 고치고, 그 페이지를 디스크에 쓰기 전에 변경 내용을 [WAL(Write-Ahead Logging)](https://www.postgresql.org/docs/current/wal-intro.html) 버퍼에 먼저 기록한다. 장애 시나리오에서는 마지막 체크포인트부터 WAL을 재실행해 복구하는 과정을 보여 주고, 스트리밍 복제로 연결된 대기(standby) 서버도 같은 화면에 나온다.

구성 요소에 마우스를 올리면 그 역할과 관련 설정값(`checkpoint_timeout`, `wal_writer_delay` 등) 설명이 표시된다. Supabase나 Neon처럼 PostgreSQL 기반 서비스를 직접 다루는 FE 개발자라면, 문서만으로는 머릿속에 그리기 어려운 프로세스와 메모리 구조를 조작해 보며 익힐 수 있다.

<img src="https://raw.githubusercontent.com/makecindy/cindy/main/.github/assets/hero-en.webp" width=500>

사용자 컴퓨터의 파일, 브라우저, 앱을 다루며 작업하는 오픈소스 AI 에이전트 [Cindy](https://cindy.app)의 클라이언트 저장소다.

Electron 데스크톱 앱(`apps/desktop`)과 Expo 기반 React Native 모바일 앱(`apps/mobile`)이 pnpm 모노레포로 구성되어 있고, 인증, 기기 연결, 에이전트 오케스트레이션, 모델 제공자 같은 공통 클라이언트 기능은 `packages/*`로 분리했다.

하네스는 여러 모델 제공자를 지원하는 경량 오픈소스 에이전트 [Pi](https://github.com/earendil-works/pi)와 Claude Code, Codex 중에서 고르며, 작업 도중에도 하네스와 모델을 바꿀 수 있다. 이때 세션은 Cindy에 남아 작업 기록, 메모리, 스킬을 그대로 이어 쓴다. 다만 하네스 내부 상태는 옮겨지지 않아, Cindy가 이전 맥락을 새 하네스에 넘기거나 다시 구성한다. 하네스와 모델을 서로 다르게 조합한 에이전트가 한 작업의 계획, 병렬 실행, 리뷰를 나눠 맡을 수도 있다. Cindy는 예약 작업과 MCP 연결도 지원하며, 모델은 Cindy 클라우드 서비스, 이미 구독 중인 Claude Code나 Codex 요금제, 개인 API 키, 로컬 모델 중에서 고른다.

공식 배포 빌드에서는 분석 서비스 TapDB로 기기 식별자를 포함한 사용 통계를 수집하는 기능이 기본으로 켜져 있다. 로그인하면 이 통계가 계정 ID와 연결되며, 기능은 설정에서 끌 수 있다. 데스크톱 앱을 로그인 없이 로컬 모드로 쓰면 통계를 보내지 않는다. 데스크톱과 모바일 에이전트 클라이언트가 공통 패키지를 나눠 쓰는 구조를 살펴보기 좋은 Apache-2.0 라이선스 프로젝트다.

## [pr-lens](https://github.com/coldteadotai/pr-lens)

<img src="https://repository-images.githubusercontent.com/1341067556/1be01955-ac56-4d8a-9682-72d3cced4c6e" width=500>

PR의 변경 내용을 애니메이션이 들어간 아키텍처 다이어그램과 데이터 흐름도로 그려 PR 화면에 보여 주는 코드 리뷰 도구다.

GitHub App, GitHub Action, CLI, 코딩 에이전트용 스킬 형태로 쓸 수 있고 GitHub, GitLab, Bitbucket을 지원한다. 아키텍처 뷰는 영향을 받는 컴포넌트를 패키지·모듈 단위 레인(열)에 나눠 배치하고 신규는 초록, 변경은 주황, 삭제는 빨강으로 표시한다. 데이터 흐름 뷰는 요청이 단계별로 이동하는 과정을 애니메이션으로 보여 주고, 화살표를 클릭하면 요청과 응답 구조에서 추가되거나 삭제된 필드를 확인할 수 있다.

분석 단계에서는 LLM을 호출한다. GitHub Action에서는 OpenAI나 Gemini처럼 OpenAI 호환 `/chat/completions` API를 제공하는 서비스의 API 키를 저장소 시크릿으로 등록하고, CLI에서는 기본 제공자인 Gemini의 `GEMINI_API_KEY` 같은 환경 변수로 키를 지정한다. 변경 코드가 이 API로 전송되므로, 사내 저장소에 적용하기 전에 보안 정책을 확인해야 한다.

```bash
export GEMINI_API_KEY=...
npx @coldtea/pr-lens-cli analyze --base origin/main
npx @coldtea/pr-lens-cli render .pr-lens/graph.json
```

모델이 다이어그램에 붙인 이름을 고치거나 분석에서 뺄 파일을 지정하는 보정 설정은 `.github/pr-lens.yml`에 둔다. 변경 파일 목록과 diff만으로는 구조를 파악하기 어려운 큰 PR을 리뷰할 때 참고할 만한 MIT 라이선스 프로젝트다.

## [ai-newtab](https://github.com/ThariqS/ai-newtab)

<img src="https://github.com/ThariqS/ai-newtab/raw/main/docs/preview.png" width=500>

브라우징 기록을 바탕으로 Claude가 매일 새 탭 페이지를 만들어 주는 Chrome 확장 프로그램이다.

에이전트는 사용자가 자주 찾는 사이트를 로그인 상태 그대로 열어 읽고, 그 내용으로 새 탭 페이지를 다시 만든다. 조간신문, 한 단짜리 요약, 대시보드, 터미널처럼 원하는 형태를 문장으로 지시하면 다음에 페이지를 만들 때부터 반영된다. 페이지 생성은 확장의 백그라운드 워커에서 실행되어 탭을 닫아도 계속되며, 페이지의 모든 링크는 에이전트가 실제로 읽은 페이지에서 가져온다. [Manifest V3](https://developer.chrome.com/docs/extensions/develop/migrate/what-is-mv3) 확장은 브라우저 확장 개발 프레임워크 [WXT](https://wxt.dev/)와 React로 만들었고, 호스트에 의존하지 않는 에이전트 로직을 별도 패키지로 분리했다.

```bash
git clone https://github.com/ThariqS/ai-newtab.git
cd ai-newtab
npx pnpm@10.11.1 install
npx pnpm@10.11.1 build
```

빌드 결과(`apps/extension/.output/chrome-mv3`)를 `chrome://extensions`에서 압축 해제된 확장으로 불러온 뒤 Anthropic API 키를 입력하면 된다. 브라우징 기록 요약과 최대 8개 페이지의 HTML이 Anthropic API로 전송되므로 README의 개인정보 항목을 먼저 읽어 봐야 한다. 브라우저 확장 안에서 에이전트를 돌리는 구조를 살펴볼 수 있는 MIT 라이선스 프로젝트다.

## [rea](https://github.com/morluto/rea)

<img src="https://raw.githubusercontent.com/morluto/rea/main/docs/assets/rea-hopper-analysis.png" width=500>

코딩 에이전트가 소스 코드 없이 앱을 분석하게 해 주는 리버스 엔지니어링용 MCP 서버이자 CLI다.

네이티브 바이너리, JavaScript와 Electron 앱, .NET 어셈블리, 웹사이트를 분석 대상으로 지원한다. 설치 명령을 실행하면 Claude Code, Codex, Cursor, Gemini CLI 등 선택한 에이전트에 MCP 서버와 작업 지침을 등록한다. 네이티브 분석에는 디스어셈블러·디컴파일러인 [Hopper](https://www.hopperapp.com/), [Ghidra](https://ghidra-sre.org/), [IDA](https://hex-rays.com/ida-pro), Kuna 중 설치된 것을 쓰며(Hopper는 `setup` 명령 실행 중 승인을 받아 설치할 수도 있다), JavaScript 정적 분석은 별도 엔진 없이 동작한다. 분석은 로컬에서 실행되고, rea는 결론마다 근거와 한계를 함께 제시한다.

```bash
npx rea-agents setup
npx -y rea-agents@latest analyze-javascript-application /absolute/path/to/app --json
```

제3자 소프트웨어를 분석하려면 라이선스와 이용 약관을 먼저 확인해야 한다. 직접 배포한 Electron 앱의 번들에 무엇이 들어갔는지 점검하거나, 소스가 남지 않은 레거시 바이너리를 분석할 때 쓸 수 있는 MIT 라이선스 프로젝트다.
