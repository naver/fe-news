## [CSS: The Bomb Inside Your Inbox](https://portswigger.net/research/css-the-bomb-inside-your-inbox)

PortSwigger Research의 Gareth Heyes가 CSS 새니타이저를 적용한 웹메일 클라이언트에서 JavaScript 없이 CSS만으로 인증 토큰을 탈취하고 키 입력을 가로채는 기법을 공개했다. Gmail, Outlook, Fastmail, ProtonMail, Yahoo Mail, AOL Mail이 테스트 대상이었다.

토큰 탈취는 속성 선택자와 중첩 CSS를 조합한 브루트포스다. 알려진 토큰 패턴을 URL 조각과 매칭시켜 일치할 때만 배경 이미지 요청이 발생하게 만들면, 요청 발생 여부 자체가 한 글자씩 정답을 알려 준다. 키로거는 `select` 요소와 `:checked` 같은 pseudo-class, 애니메이션을 조합해 구성했다. 모두 새니타이저가 허용하는 CSS·HTML 범위 안에서 동작한다.

새니타이저 우회 기법도 여러 개 제시한다.

- Chrome의 CSSOM 파싱 불일치를 이용한 "CSS mutation"
- 슬래시 사이에 이스케이프 문자를 넣어 URL 검증을 통과하는 방법
- 커스텀 data 속성을 CSS gadget으로 활용해 신뢰 경계를 넘는 방법
- 미디어 쿼리 문법으로 Outlook의 필터 로직을 교란하는 방법

OpenAI Atlas 같은 AI 브라우저에서는 CSS에 심은 간접 프롬프트 인젝션도 통한다. 대응책으로는 sandboxed iframe 격리, 키워드 화이트리스트, `select` 메뉴와 `:has`·`:checked`·`:focus` 차단, 이미지 요청 제한과 이미지 프록시를 든다. 사용자가 작성한 콘텐츠에 스타일을 허용하는 서비스라면 반드시 읽어 볼 만하다.

## [How Baseline Can Help You Ship Less JavaScript](https://www.smashingmagazine.com/2026/08/how-baseline-can-help-ship-less-javascript/)

브라우저 기능이 확장되면서 상당수 npm 의존성이 사실상 불필요해졌지만, 개발자가 패키지 목록을 재점검하는 일은 드물다. 이 글은 [Baseline](https://web.dev/baseline)을 기준으로 플랫폼이 이미 처리하는 기능을 걷어내 gzip 기준 60\~90KB를 회수하는 체계적인 감사 절차를 제안한다.

교체 후보를 클러스터로 묶어 제시하는 방식이 실용적이다.

- **국제화 계열(약 14KB)**: `timeago.js`→`Intl.RelativeTimeFormat`, `pluralize`→`Intl.PluralRules`, `numeral`→`Intl.NumberFormat`, `humanize-duration`→`Intl.DurationFormat`
- **HTTP 클라이언트(약 17KB)**: `axios`/`superagent`→`fetch` + `AbortSignal.timeout()`
- **UI 프리미티브(약 24KB)**: 모달 라이브러리→`<dialog>`, 툴팁·Popper→[Popover API](https://developer.mozilla.org/en-US/docs/Web/API/Popover_API) + anchor positioning, `focus-trap`/`body-scroll-lock`→`<dialog>` 기본 동작
- **lodash 계열(약 8KB)**: `structuredClone`, `Object.groupBy`, `Set.prototype` 메서드

다만 무조건 제거를 권하지는 않는다. 교체 전 세 가지 질문을 던지라고 한다. 우리 서비스의 실제 브라우저 지원 범위에서 안전한가, polyfill을 감안해도 번들이 실제로 줄어드는가, 플랫폼 기능이 우리 유스케이스를 모두 커버하는가. `npm ls --omit=dev --depth=0`으로 목록을 뽑고 Bundlephobia와 번들 분석기로 비용을 측정한 뒤 [webstatus.dev](https://webstatus.dev/)와 `browserslist`로 교차 검증하는 흐름을, 일회성 정리가 아니라 분기별 유지 작업으로 삼으라는 조언이 핵심이다.

## [The AI Engineering Skills Map](https://x.com/AndrewYNg/status/2088302050706686198)

<img src="https://pbs.twimg.com/media/HPsiabfXoAEz0wO.jpg" width=500>

Andrew Ng이 DeepLearning.AI 팀과 함께 정리한 AI 엔지니어링 역량 지도다. 1만 건이 넘는 채용 공고 분석, AI 전문가와 채용 담당자를 대상으로 한 구조화된 인터뷰, 설문 데이터를 종합해 지금 익힐 가치가 큰 역량을 네 가지로 추렸다.

네 가지는 AI 애플리케이션을 만들고 배포하기, 소프트웨어 엔지니어링 기본기, 코딩 에이전트 활용, 그리고 무엇을 만들지 정하는 일(shaping the build)이다. 첫째는 LLM, 컨텍스트 엔지니어링, RAG, 에이전틱 워크플로 같은 구성 요소를 이해하고 통계적 방법으로 예측 불가능한 출력을 측정하고 통제하는 능력이며, 저자는 평가(eval)와 오류 분석 루프를 규율 있게 돌리는 것을 핵심으로 꼽는다. 둘째는 비용, 확장성, 신뢰성, 속도 사이의 절충을 인지하는 힘으로, 이를 모른 채 바이브 코딩하면 에이전트가 어떤 절충을 하고 있는지조차 알 수 없다고 지적한다.

셋째는 에이전트의 컨텍스트를 관리하고, 계획과 실행 사이의 균형을 잡고, 검증기나 평가를 제공해 에이전트가 스스로 루프를 닫게 만드는 능력이다. 넷째는 명세가 주어지면 에이전트가 잘 구현해 내는 시대에 엔지니어의 일이 "명세에 무엇을 담을지 정하는 쪽"으로 옮겨 간다는 관점이다. 저자는 이 역량들이 "AI 엔지니어"라는 직함에 한정되지 않고 풀스택, 데이터, DevOps를 포함한 모든 개발자에게 필요해진다고 본다. 앞으로 무엇을 학습 우선순위에 둘지 고민하는 개발자에게 참고할 만한 정리다.

## [Dark Mode Toggles: Two States are Enough](https://lea.verou.me/blog/2026/dark-mode-toggles/)

Lea Verou가 Light/Dark/System 3단 토글이 잘못된 설계라고 주장하는 글이다. 근거는 그것이 사용자 목표가 아니라 내부 데이터 모델을 그대로 노출한 결과라는 점이다. 저자의 표현을 빌리면 "사용자는 지금 겪지 않는 문제의 해법을 찾아 나서지 않는다". 다크 모드 전환은 밝기가 불편하다고 느낀 순간에 일어나는 상황적 행동이지, 미리 정해 두는 선호가 아니다.

3단 컨트롤의 문제는 세 가지로 정리된다. 눈에 보이는 차이가 없는 선택지 사이에서 결정을 강요해 인지 부하를 늘리고 피드백 원칙을 위반한다는 점, 사용자 필요가 아닌 기술 구조를 반영한 설계라는 점, 그리고 실제 사용자 행동과 어긋난다는 점이다. 시스템이 내부적으로 세 상태를 추적해야 하는 것은 맞지만, 특정 시점에 사용자에게 의미 있는 상태는 "지금 괜찮다"와 "조정이 필요하다" 둘뿐이다.

권장 구현은 이렇다. 첫 번째 누름에서 현재 외관의 반대로 전환하고 명시적 오버라이드를 저장하며, 두 번째 누름에서 저장값을 지우고 시스템 기본값으로 복귀한다. 중요한 것은 OS 설정이 바뀌었을 때 선제적으로 저장값을 지우지 말고, 사용자 인터랙션 시점에만 시스템 선호를 재평가하는 것이다. 그래야 되돌릴 수 있는 조정이 영구 고정으로 변질되지 않는다. CSS의 `light-dark()`는 `prefers-color-scheme`을 오버라이드하는 이 시나리오에서는 아직 부족하다고 지적한다.

## [How We Migrated lovable.dev Away from Next.js](https://lovable.dev/blog/how-we-migrated-lovable-dev-away-from-nextjs)

<img src="https://lovable.dev/cdn-cgi/image/width=1080,f=auto,fit=scale-down/https://assets.lovable.dev/content/news/covers/nextjs-migration-v2.jpg" width=500>

월 4,200만 방문 규모의 lovable.dev를 Next.js에서 TanStack Start로 옮긴 기록이다. 동기가 조금 특이한데, 자사 플랫폼을 도그푸딩하면서 단일 앱 스케일링의 한계를 밀어붙여 보기 위한 것이었다. 목적지는 Cloudflare workerd 런타임 위의 TanStack Start다.

전면 재작성 대신 6개월간 두 프레임워크를 동시에 운영했다. 프록시 워커가 라우트 단위로 Next.js와 TanStack Start 사이를 분기하고, 사용자 여정에 따라 라우트를 5개 주요 그룹과 소규모 그룹 몇 개로 묶어 순차 전환했다. 공유 코드 패턴과 플랫폼 어댑터를 개발자가 먼저 잡아 둔 뒤, 실제 코드 이전은 대부분 AI 에이전트가 처리했다.

수치도 함께 공개했다. 빌드 시간은 "12분 넘는 경우가 드물지 않았다"에서 6\~9분으로 줄었고, 중위 TTFB는 49% 빨라졌지만 p90은 초기에 2배 느려졌다. 개발 환경 메모리 사용량은 Next.js 8GB에서 TanStack Start 1.5GB로 내려갔다. 코드 이전 6개월(2026년 3\~7월) 후 두 달에 걸쳐 라우트 그룹을 하나씩 내부 테스트에서 외부 트래픽 100%까지 단계 배포했다. 대규모 프로덕션 앱의 프레임워크 전환을 무중단으로 진행하는 방법론으로 참고할 만하다.

## [Migrating a Large Flow Monorepo to TypeScript](https://engineeringblog.yelp.com/2026/08/migrating-a-large-flow-monorepo-to-typescript.html)

Yelp가 570개 패키지, 140만 줄 규모의 [Flow](https://flow.org/) 코드베이스를 TypeScript로 옮긴 3년 7개월(2022년 초\~2026년 2월)의 기록이다. 타입 커버리지는 Flow 시절 83.15%에서 96.44%로 올랐다.

전면 재작성 대신 패키지 단위 점진 전환을 택했다. 대량의 `typecheck ignore` 주석을 남기는 방식은 한 번 잃은 커버리지를 회복하지 못한다는 경험 때문이었다. 기반 패키지부터 시작해 의존성 트리를 거슬러 올라가는 순서로 진행했고, `flowts`와 이후 Stripe의 `flow-to-typescript-codemod`로 자동 변환하되, `flowgen`으로 TypeScript `.d.ts`를 다시 Flow 헤더로 변환해 두 타입 시스템이 패키지 경계에서 공존하도록 만들었다. 의존성 그래프는 Graphviz로 시각화해 병목 패키지를 찾았다.

대규모 마이그레이션의 현실적인 어려움도 솔직하게 다룬다. 초기 열의가 중반에 식었을 때는 의존 영향도를 반영한 패키지 "중요도 점수"를 계산해 분기 목표에 맞춰 팀 우선순위를 조정했고, 병목이 되는 핵심 패키지는 주도 팀이 직접 전환해 "force multiplier" 역할을 했다. 결과적으로 설문에 응답한 엔지니어의 82%가 생산성 향상을 보고했고(45%는 "상당한" 향상), `swc`나 `@typescript-eslint`처럼 Flow에서 쓸 수 없던 도구를 도입할 수 있게 되었다.

## [How we raised mobile end-to-end test stability to 98%](https://shopify.engineering/mobile-e2e-testing)

<img src="https://cdn.shopify.com/b/shopify-brochure2-assets/5291f8888e656d4a8860cf7ceb00091e.png" width=500>

Shopify가 Appium과 React Native Test ID 기반 E2E 테스트를 걷어내고 컴퓨터 비전으로 갈아탄 과정이다. 기존 방식은 안정성이 50%에 그쳐 PR 체크에서 아예 제외된 상태였다. 개발자들은 하드코딩된 대기 시간으로 버티고 있었고, 테스트는 사용자 경험이 아니라 구현 세부사항을 검증하고 있었다.

새 프레임워크의 축은 두 가지다. 하나는 엄격한 빌더 API로, "모든 단계가 단언을 동반한다. 탭하거나 기다리거나 입력할 때, 그 다음에 화면에 무엇이 보여야 하는지 선언하지 않으면 진행할 수 없다". 다른 하나는 Test ID를 대체한 시각적 요소 탐지다. 텍스트는 PaddleOCR로 인식하고 아이콘은 OpenCV로 Polaris 디자인 시스템 SVG와 매칭한다. Test ID는 선택적 폴백으로만 남았다.

통합 CLI가 로컬 시뮬레이터, CI 에뮬레이터, 원격 디바이스 팜에서 동일한 테스트를 돌리고, 실패 시 시스템이 무엇을 찾고 있었는지 표시한 주석 영상을 남긴다. 가장 큰 앱의 머지를 막는 필수 CI에 새 API를 투입한 뒤 안정성은 50%에서 98%로 올랐다. 남은 실패는 네트워크 문제나 시뮬레이터 부팅 실패처럼 예상 가능한 원인들이다.

## [Haptic Feedback on the Web](https://swmansion.com/blog/haptic-feedback-on-the-web-why-the-web-deliberately-refuses-to-be-as-tactile-as-native-apps/)

웹이 네이티브 앱만큼 촉각적이지 않은 이유가 하드웨어 한계가 아니라 의도된 설계라는 점을 짚는 글이다. 표준 API인 [Vibration API](https://developer.mozilla.org/ko/docs/Web/API/Vibration_API)의 `navigator.vibrate()`는 지속 시간 시퀀스만 지정할 수 있고, 네이티브에서 쓸 수 있는 진폭·주파수·파형 제어가 없다.

브라우저가 촉각을 제한하는 이유로 세 가지를 든다. 진동 모터의 특성과 모션 센서 데이터를 결합하면 지속적인 기기 식별이 가능해지는 핑거프린팅 위험, 물리적 맥락을 추론할 수 있다는 프라이버시 우려, 그리고 사용자 동의 없이 서드파티 스크립트가 하드웨어에 접근하는 것을 막기 위해서다. Apple은 Vibration API를 아예 구현하지 않았는데, Taptic Engine의 정교한 표현력을 이 API로 담을 수 없다는 점과 핑거프린팅·오남용 우려를 이유로 들었다.

우회 수단으로는 Pulsar 같은 라이브러리가 있다. 펄스 지속 시간으로 세기를, 간격으로 주파수를 흉내 내는 PWM 방식으로 더 풍부한 촉각을 시뮬레이션한다. 표준 차원의 해법으로는 원시 모터 제어 대신 "tick" 같은 사전 정의된 효과를 사용하는 시맨틱 햅틱 방향의 Web Haptics API가 제안되어 있으며, permission policy 기본값은 `self`다.

## [The Memory Hermes Can't See: Stale Shadow Nodes in React Native](https://swmansion.com/blog/the-memory-hermes-cant-see-stale-shadow-nodes-in-react-native/)

React Native Fabric의 Shadow Node Wrapper는 뷰가 언마운트된 뒤에도 죽은 Shadow Tree 리비전에 대한 shared pointer를 붙들고 있어 메모리가 누적된다. 이 문제를 추적한 글이다. 핵심은 Hermes의 GC가 이를 볼 수 없다는 점이다. 실제 메모리는 JS 힙 밖 C++ 영역에 있고, "GC는 불투명한 JS 객체에 그만큼의 메모리가 딸려 있다는 사실을 모른다".

Tomasz J. Żelawski는 애니메이션 뷰를 반복 마운트·언마운트하는 테스트에서 산발적인 GC가 수십 MB를 한꺼번에 회수하는 것을 관찰하고 원인을 stale Shadow Node로 좁혀 갔다. 시도한 해법은 두 가지였다. 60초마다 GC를 강제하는 방식은 누적을 막았지만 오버헤드가 붙었고, Wrapper마다 2KB의 memory pressure를 등록하는 방식은 동작했지만 GC가 과도하게 돌았다. 둘 다 프로덕션에 쓸 수준은 아니었다.

진단은 명확하지만 해법은 아직 없다는 결론이고, 역설적으로 가비지를 적게 만드는 작은 앱이 이 누적 패턴에 가장 취약하다는 지적도 덧붙인다. 런타임 경계를 넘나드는 메모리를 관측 도구가 어떻게 놓치는지 보여 주는 사례다.

## [Design Tokens, Web Components, and CSS @layer](https://www.alwaystwisted.com/articles/design-tokens-and-web-components)

<img src="https://www.alwaystwisted.com/images/articles/meta-images/design-tokens-and-web-components.png" width=500>

디자인 시스템 엔지니어 Stuart Robson이 [디자인 토큰](https://www.designtokens.org/)과 웹 컴포넌트, 그리고 [`@layer`](https://developer.mozilla.org/en-US/docs/Web/CSS/@layer)가 만나는 지점의 오해를 정리한 글이다. Dave Rupert의 [How to Pierce Your Shadow Belly Button](https://daverupert.com/2026/08/how-to-pierce-your-shadow-belly-button/)에서 출발해, 토큰으로 그 해법을 자동화하는 방법을 다룬다.

핵심은 사용자 정의 속성의 값과 캐스케이드 맥락이 다른 개념이라는 점이다. 커스텀 프로퍼티 값은 [섀도 루트](https://developer.mozilla.org/en-US/docs/Web/API/Web_components/Using_shadow_DOM) 경계를 넘어 상속되지만, 문서 수준에서 선언한 `@layer` 순서는 섀도 루트 안의 캐스케이드를 통제하지 못한다. 두 트리는 각자의 레이어 순서를 따로 갖기 때문에, 토큰만으로 레이어 순서를 컴포넌트 내부에 밀어 넣을 수는 없다.

저자가 제안하는 방식은 토큰에 표식을 남기고 출력물을 둘로 나누는 것이다. `$extensions`에 네임스페이스를 붙인 확장 필드를 두어 어떤 토큰이 웹 컴포넌트용인지 표시하고, [Style Dictionary](https://styledictionary.com/) 포맷을 두 벌 만들어 섀도 루트용 `:host` 기본값과 문서 범위용 [`:defined`](https://developer.mozilla.org/en-US/docs/Web/CSS/:defined) 재정의를 각각 생성한다.

```json
{
  "$value": "{color.surface}",
  "$type": "color",
  "$extensions": {
    "com.alwaystwisted.css-layer": {
      "layer": "component.card",
      "webComponent": true
    }
  }
}
```

빌드 결과는 `@layer component.card { :host { ... } }` 형태의 섀도 루트 기본값과, 레이어 없이 선언되는 `:defined { ... }` 재정의 두 파일로 나뉜다. 디자인 토큰 파이프라인 위에서 웹 컴포넌트를 배포하는 팀이라면 스타일 적용 범위를 어디까지 자동화할 수 있는지 가늠하는 데 참고가 된다.

## [How Variable Mangling Works in Oxc Minifier](https://green.sapphi.red/blog/how-variable-mangling-works-in-oxc-minifier)

변수 맹글링은 변수 이름을 짧은 이름으로 바꿔 코드 크기를 줄이는 미니피케이션 기법이다. 이 글은 Oxc 미니파이어가 이를 어떻게 구현했는지 알고리즘 수준에서 설명한다.

단순히 모든 변수를 순서대로 `a`, `b`, `c`로 바꾸면 같은 스코프에서 동시에 살아 있는 변수에 같은 이름이 배정되어 코드가 깨진다. Oxc는 변수를 스코프 생존 구간(liveness) 기준으로 "슬롯"에 묶는다. 사용 범위가 겹치지 않는 변수끼리만 같은 슬롯을 공유하므로 정확성을 지키면서 이름 재사용을 최대화할 수 있다. 얕은 스코프의 변수부터 처리하는 순서를 택했는데, 이것이 [chordal graph](https://en.wikipedia.org/wiki/Chordal_graph)의 Perfect Elimination Ordering의 역순에 해당해 최적의 슬롯 배정이 보장된다.

이름을 배정하는 문자 순서도 단순 알파벳 순이 아니다. 미니파이된 코드에서 자주 등장하는 문자 빈도를 반영해 정렬하는데, gzip 압축률을 높이기 위해서다. 번들러가 내부에서 실제로 어떤 판단을 내리는지 궁금했다면 좋은 사례 연구다.

## [Progressive Enhancement Inside of JavaScript](https://remysharp.com/2026/08/05/progressive-enhancement-inside-of-javascript)

점진적 향상은 보통 JavaScript가 아예 없을 때를 다루지만, 이 글은 JavaScript가 "아직 로드되지 않은" 구간을 다룬다. Remy Sharp의 마크다운 도구는 압축 기준 600KB의 의존성을 내려받는데, 느린 회선에서 코드가 준비되기 전에 사용자가 파일을 드롭하면 브라우저가 이를 파일 열기로 해석해 페이지를 벗어나 버렸다.

해법은 JavaScript 내부에서도 관심사를 분리하는 것이다. HTML 직후에 인라인으로 최소한의 코드를 두어 이벤트 핸들러를 바인딩하고 시각적 피드백을 준 다음, 무거운 의존성(마크다운 파서, syntax highlighter)이 다운로드·파싱될 때까지 사용자 동작을 큐에 쌓아 둔다. 로드가 끝나면 큐에 담긴 작업을 실제 렌더링 로직으로 흘려보낸다. 저자의 표현대로 "사용자 인터랙션을 우선하고 꼭 필요한 JavaScript만 인라인으로 포함함으로써, 인터랙션을 붙잡아 두고 작업을 큐에 쌓을 수 있었다".

저자는 [Netlify ODB(On-Demand Builders)](https://docs.netlify.com/build/configure-builds/on-demand-builders/) 같은 서버 사이드 렌더링이 더 빠를 수 있다고 보면서도 직접 측정하지는 않았다고 밝힌다. GPRS 수준 회선에서는 완료까지 2분 가까이 걸리지만 인터랙션 자체는 끝까지 동작한다. 번들 크기를 줄이기 어려운 도구형 웹앱이라면 참고할 만한 패턴이다.

## [Reliable Query Prefetching with TanStack Router](https://tkdodo.eu/blog/reliable-query-prefetching-with-tanstack-router)

라우트 로더에서 데이터를 미리 가져오고 컴포넌트에서 같은 쿼리를 구독하는 패턴은 폭포수를 없애는 표준 해법이지만 함정이 있다. tkdodo의 표현대로 "그 두 곳이 100% 동기화되어" 있어야 한다는 점이다. 앱이 커질수록 이 동기화는 깨지기 쉽다. 컴포넌트에 `?asOf=YYYY-MM-DD` 같은 검색 파라미터를 추가하면서 로더를 함께 고치는 것을 잊으면 프리페치가 빗나가 불필요한 요청과 폭포수가 다시 생긴다.

해법은 queryOptions를 라우트 컨텍스트로 끌어올리는 것이다. `params`나 `loaderDeps`가 바뀔 때마다 실행되는 `context` 함수에서 queryOptions를 한 번만 만들고, 로더의 `ensureQueryData`와 컴포넌트의 `useSuspenseQuery`가 `Route.useRouteContext()`로 같은 객체를 가져다 쓴다. 중복이 사라지므로 둘이 어긋날 수가 없다.

부수 효과도 좋다. 컨텍스트는 중첩 라우트로 상속되고, 관련 없는 검색 파라미터를 구독해 불필요한 리렌더가 발생하는 일도 막아 준다. 흔한 버그의 원인을 단일 진실 공급원 패턴으로 정리하는 정석적인 접근이다.

## [How AI text watermarking works: a visual guide](https://declaude.org/watermarking/)

<img src="https://declaude.org/watermarking/og.png?v=2" width=500>

AI가 생성한 텍스트에 눈에 보이지 않는 표식이 어떻게 새겨지는지를 다섯 단계로 나눠 시각적으로 설명하는 가이드다. AI 문체를 평범한 산문으로 고쳐 쓰는 도구인 [declaude](https://declaude.org/)가 함께 공개한 자료다.

설명의 출발점은 워터마크가 글자가 아니라 "단어와 단어 사이의 선택"에 숨는다는 점이다. 모델은 매 위치마다 여러 개의 그럴듯한 후보 중 하나를 고르는데, 이 여유 공간에 비밀 키로 후보를 초록과 빨강으로 나누고 초록 쪽으로 확률을 살짝 기울인다. 색 구분은 앞뒤 문맥에 따라 달라지므로 같은 단어라도 위치에 따라 색이 바뀌며, 기울임이 약해서 빨간 단어도 종종 그대로 나온다. 검출은 키를 가진 쪽이 같은 방식으로 다시 색을 칠해 초록 비율을 세는 식이다. 표식이 없는 글은 대략 50%에 수렴하지만 워터마크가 있는 글은 통계적으로 그 이상이 나온다.

실무적으로 중요한 부분은 마지막 두 단계다. 검출은 원문 표현이 짧게라도 이어져 남아 있어야 성립하므로 가벼운 편집은 표식을 희석하는 정도지만, 표현이 전혀 겹치지 않게 다시 쓰면 사실상 지워진다. 또한 키를 가진 쪽만 검증할 수 있어 공개된 "AI 탐지기" 사이트로는 확인할 수 없고, 검출 결과는 "AI가 썼다"가 아니라 "AI를 거쳤다"에 가깝다는 점도 짚는다. 문서에서는 [Kirchenbauer 등의 초기 방식](https://arxiv.org/abs/2301.10226)과 Google의 [SynthID](https://deepmind.google/technologies/synthid/) 토너먼트 방식을 참조로 들면서, 실제 상용 구현의 세부는 공개되지 않았다고 밝힌다.

## [pnpm 12](https://pnpm.io/blog/whats-different-in-pnpm-12)

pnpm을 Rust로 재작성한 pnpm 12가 v12.0.0부터 정식 릴리스되었다. 다만 npm `latest` 태그는 아직 pnpm 11 계열을 가리키므로 `next-12` 태그로 설치해야 한다. 마이그레이션이라 부를 만한 작업은 없다. 명령어, 플래그, 설정, lockfile 포맷을 pnpm 11과 그대로 공유하며 문서도 두 버전에 함께 적용된다.

동작이 달라진 지점은 일곱 가지다.

- 전역 설치된 Node·Deno·Bun이 `devEngines.runtime`에 고정된 프로젝트 버전을 따르게 되어 별도 버전 매니저가 필요 없어졌다.
- GitHub·GitLab·Bitbucket 의존성은 전송 방식과 무관하게 정규 HTTPS URL로 해석되어, 머신마다 SSH 설정 때문에 설치가 깨지는 문제가 사라졌다.
- `pnpm add -g yarn`은 npm 패키지가 아니라 실제 패키지 매니저를 설치하므로 Classic이 아닌 최신 Yarn이 설치된다.
- 순환 의존성은 패키지 ID 순으로 정렬해 바이트 단위로 동일한 lockfile을 만든다. 순환이 많은 대규모 워크스페이스에서는 peer 해석이 2\~3배 빨라지고 메모리 사용량이 약 25% 줄어든다.

- `--resolution-only` 플래그는 제거되었고 `pnpm peers check`로 대체된다.

```bash
dembrandt dembrandt.com --crawl 10
```

기존 서비스의 스타일을 토큰으로 옮기거나, 배포된 화면이 디자인 시스템에서 얼마나 벗어났는지 확인하려는 팀이 참고할 만한 MIT 라이선스 프로젝트다.

## [TermDOM](https://termdom.org/)

<img src="https://termdom.org/static/logo.svg" width=200>

HTML과 CSS를 터미널에 렌더링하는 라이브러리다. 스펙을 따르는 DOM·CSSOM API를 구현했기 때문에, TUI와 CLI를 순수 JavaScript로 쓰거나 프런트엔드 프레임워크를 그대로 얹어 만들 수 있다. React와 Vue가 최소한의 설정으로 동작하고, Prism처럼 브라우저용으로 만들어진 라이브러리도 수정 없이 쓸 수 있다.

flexbox, grid, table, CSS 박스 모델을 지원하며 색상은 터미널 팔레트로 해석되고 텍스트 장식은 ANSI 속성(bold, italic, underline, strikethrough)으로 렌더링된다. Node.js 20 이상이 필요하고 MIT 라이선스다.

```javascript
import { TermDOM } from "@b9g/termdom";

const term = new TermDOM();
term.attach();

const heading = term.document.createElement("div");
heading.style.backgroundColor = "blue";
heading.textContent = "Hello, terminal";
term.document.body.appendChild(heading);
```

CLI 도구의 UI를 만들 때마다 별도 TUI 프레임워크를 배워야 했던 부담을 이미 아는 웹 기술로 대체할 수 있다.

## [hunk](https://www.hunk.dev/)

<img src="https://www.hunk.dev/shot-github-dark.webp" width=500>

리뷰를 우선에 둔 터미널 diff 뷰어로, 에이전트가 만든 변경을 사람이 읽는 상황을 전제로 설계되었다.

터미널 폭에 따라 좌우 분할과 상하 적층 배치를 자동으로 바꾸고, 여러 파일의 변경을 위에서 아래로 이어지는 하나의 흐름으로 보여 준다. 특징적인 기능은 에이전트 주석을 diff 안에 직접 얹는 것으로, 왜 이렇게 바뀌었는지를 해당 변경 옆에서 확인할 수 있다. Catppuccin, Gruvbox, GitHub 등 60여 종의 테마로 실제 구문 강조를 적용하고, 키보드 우선 조작에 마우스도 지원하며, 변경을 실시간으로 다시 읽는 감시 모드가 있다.

Git 외에 [Jujutsu](https://jj-vcs.github.io/jj/), [Sapling](https://sapling-scm.com/)을 지원하고 페이저나 difftool로도 붙여 쓸 수 있다. 기능 확장은 TypeScript 플러그인으로 한다.

```bash
npm i -g hunkdiff   # 또는 brew install hunk

hunk diff   # 작업 트리 변경 검토
hunk show   # 특정 커밋 확인
```

에이전트가 만든 변경을 터미널을 벗어나지 않고 검토하고 싶은 개발자가 시도해 볼 만한 MIT 라이선스 프로젝트다.

## [glow](https://github.com/charmbracelet/glow)

<img src="https://stuff.charm.sh/glow/glow-banner-github.gif" width=500>

터미널에서 마크다운을 읽기 좋게 렌더링해 주는 Charm의 CLI 도구로, 지난 8월 v3가 공개되었다.

현재 디렉터리나 Git 저장소 안의 마크다운 파일을 훑어보는 TUI 모드와, 파일, 표준 입력, GitHub/GitLab 저장소, HTTP URL을 받아 바로 출력하는 CLI 모드를 함께 제공한다. `less`와 비슷한 키 조작의 페이저를 내장했고, `-w`로 줄바꿈 폭을 지정하거나 `-s`로 미리 정의된 dark와 light 스타일 또는 직접 만든 JSON 스타일시트를 적용할 수 있다. 설정은 `glow.yml`에 저장해 두고 쓴다.

v3는 UX 변경 없이 Bubble Tea, Lip Gloss, Bubbles를 각각 v2로 올린 조용한 릴리스로, 렌더링이 더 빠르고 정확해졌다. Go 패키지 경로가 `charm.land/glow/v3`로 바뀐 점은 유의해야 한다.

```bash
brew install glow          # 또는 go install charm.land/glow/v3@latest

glow README.md
glow github.com/charmbracelet/glow
glow -w 60 -s dark file.md
```

에이전트가 쏟아 내는 마크다운 산출물을 터미널에서 그대로 확인할 일이 많아진 요즘 다시 꺼내 볼 만한 MIT 라이선스 프로젝트다.

## [skill-recorder](https://github.com/microsoft/skill-recorder)

<img src="https://github.com/microsoft/skill-recorder/raw/main/docs/images/library.png" width=500>

화면에서 실제로 일하는 과정을 녹화한 뒤 이를 재사용 가능한 에이전트 스킬이나 자동화로 바꿔 주는 Microsoft의 데스크톱 앱이다.

클릭, 앱과 창 전환, URL, 그리고 선택적인 음성 해설을 로컬에서 수집하고, [GitHub Copilot CLI](https://github.com/github/copilot-cli)가 이를 분석해 "무엇을 하려 했는가"라는 의도 문장과 순서가 있는 절차 단계로 재구성한다. 해설 녹음은 [Whisper](https://github.com/openai/whisper)로 기기 안에서 99개 언어를 전사한다. 눈에 띄는 설계는 UI 동작을 그대로 재생하기보다 대응하는 CLI 명령을 우선하도록 유도한다는 점으로, 덕분에 녹화한 한 건이 비슷한 다른 작업에도 일반화된다.

## [fx](https://github.com/vercel-labs/fx)

<img src="https://fx.sh/og.png" width=500>

Vercel Labs가 [Zig](https://ziglang.org/)로 작성한 최소한의 코딩 에이전트 CLI다.

터미널 위의 무거운 IDE보다 유닉스 셸에 가깝게 만드는 것을 목표로 삼아, 시스템 프롬프트 설계부터 도구 구성과 기능 범위까지 전반을 줄였고 바이너리 크기는 7.8MiB다. 네이티브 바이너리 외에 WebAssembly 모듈로도 배포되며, `createFxAgent()`로 에이전트 코어를, `createFxTerminal()`로 인터랙티브 터미널을 각각 임베드하는 실험적 SDK를 제공한다. [Agent Client Protocol](https://agentclientprotocol.com/) 연동을 위한 `fx acp` 명령도 있다.

스킬, [MCP](https://modelcontextprotocol.io/), 서브에이전트로 기능을 확장하고, 장시간 실행되는 프로세스를 위한 지속형 터미널 세션과 ID나 작업 공간 단위의 세션 재개를 지원한다. 권한은 기본이 auto 모드로, 일상적인 개발 동작은 그대로 실행하고 판단이 필요한 동작만 좁은 범위의 안전 검토를 거친다. 모델은 [Vercel AI Gateway](https://vercel.com/docs/ai-gateway), OpenAI Codex, xAI Grok 인증 경로를 지원한다.

```bash
curl -fsSL https://fx.sh/setup.sh | bash

fx login
fx                 # 인터랙티브 세션
fx ask "explain the changes in this repository"
```

코딩 에이전트를 자체 제품에 끼워 넣거나 하네스 구조를 뜯어보려는 개발자가 살펴볼 만한 Apache 2.0 라이선스 프로젝트다.

## [herdr](https://github.com/herdrdev/herdr)

<img src="https://github.com/herdrdev/herdr/raw/master/assets/logo.png" width=200>

코딩 에이전트가 상주하는 것을 전제로 설계한 백그라운드 서버 런타임이다.

터미널 창을 닫거나 네트워크가 끊겨도 각 페인(pane)이 서버 쪽에서 계속 살아 있어 에이전트가 하던 작업을 이어 간다. 페인마다 작업 중, 대기 중, 유휴 중 어느 상태인지 표시되므로 여러 에이전트를 동시에 돌릴 때 무엇이 사람 입력을 기다리는지 한눈에 파악할 수 있다. Claude Code, Codex, Cursor 같은 에이전트가 CLI와 소켓 API로 직접 런타임을 제어할 수 있게 만든 점이 일반 [터미널 멀티플렉서](https://github.com/tmux/tmux)와 다른 부분이다.

조작은 tmux 계열 단축키와 마우스를 모두 지원하고, 플러그인으로 기능을 확장할 수 있는 마켓플레이스도 함께 제공한다. Rust로 작성한 단일 바이너리라 Electron 같은 런타임 의존이 없다.

```bash
curl -fsSL https://herdr.dev/install.sh | sh   # 또는 brew install herdr

herdr          # 서버 시작
# Ctrl+B Q 로 분리(detach)
herdr          # 기존 세션에 다시 연결
```

에이전트를 하루 단위로 길게 굴리면서 세션이 끊겨도 작업이 살아 있기를 바라는 개발자가 참고할 만한 Apache 2.0 라이선스 프로젝트다.

## [loopx](https://github.com/huangruiteng/loopx)

<img src="https://raw.githubusercontent.com/huangruiteng/loopx/main/docs/assets/loopx-social-preview.png" width=500>

며칠에서 몇 주에 걸치는 장기 에이전트 작업을 관리하는 제공자 중립 제어 평면(control plane)이다.

기존 하네스를 대체하지 않고 그 위에 얹히는 지속 상태 커널로 동작한다. 목표, 할 일, 통과 조건(gate), 근거, 사용량 한도를 여러 턴에 걸쳐 보존하므로 세션이 끊기거나 다시 시작해도 진행 상태가 이어진다. 여러 에이전트가 동료로 참여해 작업을 점유하고 임차(lease)한 뒤 결과를 넘겨주는 협업 구조와, 사용량 한도, 안전한 대체 경로, 근거가 남는 결정 이력 같은 통제 장치를 함께 제공한다. Codex App, Claude Code, KunlunCode, DeepSeek Harness 및 직접 만든 러너와 연동되며, 목표와 진행 상황을 확인하는 읽기 중심의 로컬 대시보드가 딸려 있다.

```bash
python3 -m pip install --upgrade loopx
loopx workflow-skills --install
loopx doctor

cd /path/to/your-project
loopx connect
loopx status
```

Python 3.11 이상이 필요하다. 저장소는 200시간이 넘게 이어진 실제 루프의 궤적을 오픈소스 기여와 ML 실험 사례로 공개하고 있다. 짧은 대화 단위를 넘어서는 작업을 에이전트에게 맡기려는 팀이 참고할 만한 Apache 2.0 라이선스 프로젝트다(v0.4.8 이전 릴리스는 MIT).
