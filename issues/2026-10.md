# 📚 링크 & 읽을거리

## [The Story of VS Code](https://www.youtube.com/watch?v=kHL3XzjpT5w)

<img src="https://i.ytimg.com/vi/kHL3XzjpT5w/maxresdefault.jpg" width=500>

Visual Studio Code 공식 채널이 2026년 9월 4일 공개한 약 1시간 38분 분량의 다큐멘터리다. 2024년 11월부터 2026년 중반까지 촬영했고, 초기 취리히 팀 엔지니어와 TypeScript 공동 창시자 Steve Lucco, GitHub Copilot 프로젝트를 시작한 Oege de Moor, GitLens 제작자 Eric Amodio, Wes Bos 등 30여 명이 출연한다. Windows와 C#, C++ 개발자만 바라보던 Microsoft 개발자 사업부(Developer Division)가 "개발자가 있는 곳으로 찾아간다"로 방향을 바꾼 배경에서 이야기가 시작된다.

2010년 무렵 브라우저가 애플리케이션 플랫폼으로 떠오르자 Microsoft는 『[Design Patterns](https://en.wikipedia.org/wiki/Design_Patterns)』 공저자로 IBM에서 여러 IDE를 만든 [Erich Gamma](https://en.wikipedia.org/wiki/Erich_Gamma)를 영입해 취리히에서 브라우저 기반 개발 도구를 만들게 했다. 팀의 첫 결과물인 [Monaco Editor](https://github.com/microsoft/monaco-editor)는 jQuery를 쓰지 않고 줄마다 div, 토큰마다 span을 직접 다루는 렌더링 코드로 작성했으며, 무거운 계산은 UI 스레드 밖에서 처리하고 화면에 보이는 줄만 그리는 원칙을 처음부터 지켰다. 이 팀은 초기 TypeScript 컴파일러의 첫 사용자로서 TypeScript 설계에 피드백을 주기도 했다. 웹 IDE인 Visual Studio Online Monaco가 Azure 웹사이트 편집이라는 좁은 용도에 머물자 팀은 node-webkit과 Electron으로 데스크톱 편집기를 만들어 Build 컨퍼런스에서 Linux, macOS, Windows용 VS Code를 발표했다. 확장을 별도 프로세스에서 실행하고 한번 공개한 API는 바꾸지 않는 원칙(10년 전에 만든 확장도 지금 설치해 실행할 수 있다), TypeScript 서버에서 출발해 JSON-RPC 기반 오픈 프로토콜로 정리한 [LSP(Language Server Protocol)](https://microsoft.github.io/language-server-protocol/), UI 프로세스와 확장 호스트 프로세스를 분리한 구조 덕분에 가능했던 원격 개발과 vscode.dev의 탄생 과정도 설명한다.

후반부는 AI가 바꾼 개발 환경을 보여준다. Oege de Moor는 2020년 초 훗날 GPT-3가 되는 모델에 옥스퍼드 교수 시절의 면접 문제 50개를 풀게 했을 때는 모두 틀렸지만, 테스트 커버리지가 높은 함수의 본문을 지우고 모델이 채우게 한 뒤 테스트를 다시 돌리자 3분의 1 이상을 맞혔다고 회상한다. 이후 VS Code 팀은 Ask, Edits, Agent Mode 순으로 AI에 맡기는 범위를 넓혔고, Chat과 코드 완성 기능의 소스를 공개했으며, 월 단위였던 릴리스 주기를 주 단위로 바꾸고 있다. Cursor, Windsurf, Antigravity 같은 포크에 대해서는 개발 방식의 발전을 앞당긴다는 점에서 VS Code를 오픈 소스로 공개한 이유와 다르지 않다는 시각을 밝힌다. 내부 API를 허용하지 않는 확장 모델 같은 초기 아키텍처 결정이 10년 뒤 원격 개발, 브라우저 버전, AI 기능까지 뒷받침한 과정은 오래 유지할 제품의 구조를 고민하는 FE 개발자에게 참고가 된다.

## [Native is now the future of mobile at Shopify](https://shopify.engineering/back-to-native)

<img src="https://cdn.shopify.com/b/shopify-brochure2-assets/74f109ae9b0c3034a78a3b63294ae2e6.png" width=500>

2020년 [React Native](https://reactnative.dev/) 전면 도입을 선언했던 Shopify가 모바일 앱을 다시 Swift와 Kotlin 네이티브로 옮긴다고 발표했다. React Native가 실패해서가 아니라, 코딩 에이전트 덕분에 같은 기능을 두 플랫폼에 각각 만드는 비용이 크게 줄었기 때문이다. 공유 구현의 이점은 줄어든 반면 플랫폼 기능과 퍼스트파티 도구에 가까이 있다는 네이티브의 이점은 그대로 남았다는 판단이다.

마이그레이션은 점진 전환이 아니라 새로 만드는 방식을 택했다. Shop 앱은 개념 증명부터 스토어 출시까지 12주 만에 네이티브로 재구축했고, 300개가 넘는 화면을 가진 Shopify 앱도 올해 안에 출시할 예정이다. LLM에 기존 코드를 통째로 넘겨 한 번에 옮기면 유지보수할 수 없는 코드가 쏟아지기 때문에 Helix라는 시스템을 만들었다. Helix는 화면 하나를 몇 분 안에 리뷰할 수 있는 작은 체크포인트로 나누고, 각 체크포인트가 테스트, 실행 중인 앱과의 시각 비교, 두 개의 적대적 코드 리뷰, 사람의 승인을 모두 통과해야 다음 단계로 넘어가게 한다. 시뮬레이터 조작이 에이전트의 병목이라는 점도 짚는다. 비즈니스 로직을 UI와 완전히 분리해 데스크톱에서 헤드리스로 실행하고, 이를 CLI로 에이전트에 노출해 피드백 주기를 분 단위에서 밀리초 단위로 줄였다.

Shopify가 관리해 온 오픈소스의 향방도 정리했다.

- [React Native Skia](https://github.com/Shopify/react-native-skia): 2026년 말까지 후원을 이어 가고, 이후 William Candillon이 포크해 새 이름으로 배포한다.
- [FlashList](https://github.com/Shopify/flash-list): 주간 약 200만 다운로드. 호환성을 깨는 치명적 이슈는 계속 수정하며 장기 관리 주체를 찾고 있다.
- [Restyle](https://github.com/Shopify/restyle): 2026년 말까지 유지한 뒤 아카이브한다.

코딩 에이전트로 기술 선택의 전제가 바뀌었을 때 이를 재평가하는 과정을 보여 주는 사례이며, 위 라이브러리를 쓰는 React Native 프로젝트라면 전환 일정을 확인해 둬야 한다. Shop 앱 전환 과정은 [별도 글](https://shopify.engineering/shop-app-migration)에 자세히 정리되어 있다.

## [How our agents build on-brand pages with design.md](https://vercel.com/blog/how-our-agents-build-on-brand-pages-with-design-md)

<img src="https://assets.vercel.com/image/upload/contentful/image/e5382hct74si/5F2lrV1tu5qQsQiSSll8GA/7ee5274fbd32707cdd76a176dbc04f47/sandbox-Network-Boundary__1_.png" width=500>

Vercel이 코드 저장소 밖에서도 코딩 에이전트가 Vercel다운 페이지를 만들 수 있도록 공개 파일 하나로 디자인 지침을 제공하는 [design.md](https://vercel.com/design.md)를 만든 과정이다. 저장소 안에서는 [product-design 스킬](https://vercel.com/blog/teaching-agents-product-design-at-vercel)이 실제 컴포넌트와 예시를 곁에 두고 동작하지만, 보고서나 제안서처럼 다른 도구에서 만드는 페이지에는 그 맥락이 없다. 기존 스킬을 공개 프롬프트로 합쳐 봤더니 모델마다 같은 문장을 다르게 해석해 결과가 제각각이었다고 한다.

그래서 처음부터 다시 쓰면서 모든 변경을 7개의 고정된 평가 시나리오(사용량 보고서, 갱신 제안서, 발표 자료 등)로 검증했다. 결과물은 세 부분으로 정리되었다.

- **design.md**: 독자가 페이지에서 할 일, 근거 배치, 구성 방식에 대한 판단 지침. 생성형 디자인에서 반복되는 나쁜 패턴에 이름을 붙여 피하게 한다.
- **공개 스타일시트**: 헤더, 표, 차트 스타일 같은 디자인 시스템 요소를 클래스와 토큰으로 제공한다. 에이전트는 클래스 이름만 쓰고 CSS는 브라우저에서 로드되므로 모델 컨텍스트를 차지하지 않는다.
- **평가 루프**: 표가 가용 너비를 쓰지 않는 문제처럼 기계적인 실패는 코드 검사로, 위계와 구성 같은 주관적 판단은 사람의 블라인드 A/B 비교로 다룬다.

200회 넘는 실행을 거쳐 만들었고, Vercel이 GPT-5.5로 측정한 결과 design.md를 적용한 페이지의 알려진 실패는 39건으로 미적용(91건)보다 57% 적었다. 다만 표본이 6페이지에 불과하고 이미 알고 있는 실패만 잡는다는 한계도 함께 밝힌다. 글 말미에는 반복되는 산출물 하나를 골라 기준 결과를 저장하고, 최근 교정 사항 10개를 관찰 가능한 규칙으로 바꿔 비교하는 단계별 방법을 제시한다. 사내 디자인 시스템을 에이전트가 따르게 하려는 팀이 참고할 만하다.

## [AI coding has made CI a bottleneck, so we reworked ours to keep up](https://linear.app/now/ci-bottleneck-reworked)

<img src="https://webassets.linear.app/images/ornj730p/production/eda443893b72237b999b27ca5e953b82dfc33f9d-3904x2574.png?q=95" width=500>

에이전트로 코드를 내놓는 속도는 빨라졌지만 모든 PR이 거치는 CI는 그만큼 빨라지지 않았다. Linear 엔지니어 Mufeez Amjad가 TypeScript 위주의 코드베이스에서 올해 들어 테스트 묶음이 약 4배로 늘어나는 동안 PR의 CI 대기 시간을 6분 이상에서 5분 남짓으로 줄이고, 테스트당 러너 시간을 약 절반으로 낮춘 과정을 정리한 글이다.

개선 작업은 네 가지로 나뉜다.

- **인프라와 도구 교체**: GitHub Actions 기본 러너에서 서드파티 러너로 옮겨 작업이 평균 34% 빨라졌다. 네이티브 TypeScript 컴파일러 [tsgo](https://github.com/microsoft/typescript-go)로 바꾼 뒤 타입 검사 시간의 주간 중앙값이 73% 줄었다. 타입 정보를 쓰던 커스텀 린트 규칙을 AST 기반 정적 분석으로 다시 작성해 ESLint에서 TypeScript 의존을 없앴고(API 린트 시간 68% 감소), 이후 [Oxlint](https://oxc.rs/docs/guide/usage/linter)로 옮기기도 쉬워졌다.
- **다른 작업을 막는 선행 작업 최적화**: 변경 경로를 확인하는 작업은 fetch 깊이를 제한하거나 체크아웃을 없애 중앙값을 26초에서 8초로 줄였다. 네트워크 문제로 멈추던 `actions/checkout`은 재시도와 `GIT_HTTP_LOW_SPEED_LIMIT`, `GIT_HTTP_LOW_SPEED_TIME` 설정을 넣은 자체 composite action으로 교체했다.
- **반복 준비 작업 줄이기**: Postgres 클라이언트를 CI 기본 이미지에 미리 설치하고, pnpm 설치를 API 패키지로 한정해 44\~73초를 16\~18초로 줄였다. `node_modules` 캐시는 복원(약 28초)이 필터링 설치(약 7.5초)보다 느려 쓰지 않는다. 마이그레이션 전체를 재실행하던 DB 준비는 스키마 스냅샷 로딩으로 바꿨고, 짧은 검사 7개를 작업 2개로 합쳐 러너 시간을 월 약 87,000분(전체 CI 사용량의 11.8%) 절약했다.
- **테스트 실행 효율화**: [Vitest](https://vitest.dev/)는 테스트 시간이 아니라 파일 단위로 작업을 나누기 때문에 큰 테스트 파일을 쪼개고 샤드를 4개에서 8개로 늘렸다. 안전하다고 표시한 파일만 [`isolate: false`](https://vitest.dev/config/isolate)로 모듈 레지스트리를 공유하게 한 것이 가장 큰 개선으로, 가장 느린 샤드가 300\~379초에서 약 195초로 줄었다.

`isolate: false`는 정확성 위험이 커서 파일마다 옵트인 주석을 달고 공유 상태 정리 코드를 추가했으며, 테스트 대부분을 에이전트가 작성하므로 에이전트 스킬에도 같은 제약을 반영했다. 샤드를 늘리는 효과는 샤드당 고정 준비 비용이 낮아야 나온다는 점도 강조한다. 에이전트 도입으로 PR 수가 늘어난 팀이라면 CI 구성을 점검할 때 참고할 수 있는 수치가 많은 글이다.

## [Brownfield Agentic Engineering](https://addyo.substack.com/p/brownfield-agentic-engineering)

<img src="https://substackcdn.com/image/fetch/$s_!PyjB!,w_1200,h_675,c_fill,f_jpg,q_auto:good,fl_progressive:steep,g_auto/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Ff9f7e7a8-831e-4f36-8ad6-b46fe44fbc79_2754x1536.jpeg" width=500>

Addy Osmani가 오래된 코드베이스에 코딩 에이전트를 투입할 때 필요한 원칙을 정리한 글이다. [브라운필드(brownfield)](https://en.wikipedia.org/wiki/Brownfield_(software_development)) 시스템은 저장소만으로는 실제 동작을 다 설명할 수 없는 시스템이다. 저자는 이런 곳에서 에이전트를 감독 없이 돌리면 "동작은 하지만" 설계가 틀리고 테스트가 취약한 결과를 얻기 쉽다고 경고한다. 핵심은 숨은 제약을 드러내고, 작은 변경을 믿을 수 있게 만드는 것이다.

저자는 여섯 가지를 제안한다.

- **구역 나누기**: 테스트가 충분하고 격리된 green, 품질이 섞인 yellow, 인증, 결제, 권한처럼 민감한 red로 코드베이스를 나눈다. 지도는 에이전트가 아니라 사람이 그리고, yellow는 특성화 테스트가 생기고 담당자가 첫 변경을 검토한 뒤에야 green이 된다
- **코드가 말하지 못하는 것만 문서화**: 에이전트는 코드에서 구조를 잘 추론하므로, 비즈니스 맥락이나 직관에 어긋나는 구현의 배경처럼 코드에 없는 정보만 적는다
- **조사 결과를 남기기**: 진입점, 담당자, 호출자, 기존 테스트, 열린 질문을 담은 짧은 메모를 만들어 다음 세션이 같은 탐색을 반복하지 않게 한다
- **반복되는 리뷰 코멘트는 도구로**: 같은 지적이 또 나오면 lint 규칙, 훅, 타입, 테스트, 스킬로 옮긴다
- **위험 없는 작업부터**: 현재 동작을 고정하는 [특성화 테스트(characterization test)](https://en.wikipedia.org/wiki/Characterization_test)를 먼저 만들되, 같은 에이전트 세션이 테스트와 구현을 모두 쓰지 않게 한다
- **마이그레이션은 완결 단위로**: 옛 경로를 제거해야 완료다. 절반만 진행된 마이그레이션은 에이전트에게 서로 모순된 선례를 보여 준다

병렬화는 가장 마지막에 하라고 권한다. 병렬화는 이미 있는 병목을 키울 뿐이라는 이유다. 또 에이전트는 모호함의 비용을 드러낸다고 말한다. 문서화되지 않은 팀 관례가 반복되는 리뷰 코멘트로 나타나기 때문이다. Bun의 Zig→Rust 포팅, Asana의 Enzyme 제거, Shopify의 앱 재작성 등 대규모 사례도 함께 소개하니 레거시 FE 코드베이스에 에이전트를 도입하려는 팀이라면 읽어 볼 만하다.

## [Using Claude Code: Spending your effort](https://claude.dev/blog/spending-your-effort/)

Anthropic의 Thariq Shihipar가 Claude Code의 effort 설정이 실제로 무엇을 바꾸는지 직접 실험과 Terminal-Bench 3.0 결과로 분석한 글이다. effort는 모델에게 과제에 쓸 연산량을 대략 알려 주는 값으로, 높일수록 Claude가 검증과 엣지 케이스 테스트를 더 하고 스스로 판단하는 범위도 넓어진다.

Opus 5.5로 "피트니스 기록 앱을 만들어 달라"는 모호한 요청을 실행하자 low에서는 1.5분 만에 로그와 그래프만 나왔고, max에서는 67분에 걸쳐 히트맵까지 갖춘 앱이 나왔다. 반면 사양을 자세히 준 경우에는 effort에 따른 결과 차이가 크지 않았다. 어려운 과제에서는 차이가 분명했다. JavaScript 삽입 경로를 모두 막는 HTML 새니타이저 과제(`html-js-filter`)에서 Fable 5.1은 low에서 5회 중 1회, xhigh에서 5회 모두 성공했다. 높은 effort에서는 초안을 적대적으로 검토하고, 파서 소스를 읽고, XSS 테스트 묶음과 무작위 문서 퍼저까지 돌렸다. Anthropic 내부 실행 기준으로 low에서 최고 effort로 올렸을 때 통과율은 보안 64%→87%, 하드웨어 34%→75%, 소프트웨어 43%→56%였다. effort를 높이면 엣지 케이스 누락은 줄지만 접근 방식 자체가 틀린 실패는 고쳐지지 않았다.

저자는 작업 성격에 따라 effort를 네 단계로 나눠 쓰라고 권한다.

- **low**: 브레인스토밍, 스케치, 간단한 수정처럼 빠르게 주고받을 때
- **medium**: 새 기능 구현 같은 일반적인 개발 작업
- **high**: 기존 코드베이스의 버그 수정처럼 검증과 엣지 케이스가 중요한 작업
- **max**: 앱을 처음부터 끝까지 만들고 검증하거나 보안 취약점을 찾는 등 완전 자율 작업

새 기능 개발에서는 사양을 주고 Claude가 빠진 내용을 질문하게 한 뒤, low로 구현과 반복을 하고 high로 검증하는 흐름을 권한다. Claude Code에서는 `/effort` 명령으로 대화 중에도 수준을 바꿀 수 있다.

## [How I Vibed a Proof of Conway’s Conjecture](https://overreacted.io/how-i-vibed-a-proof-of-conways-conjecture/)

<img src="https://overreacted.io/how-i-vibed-a-proof-of-conways-conjecture/opengraph-image?5b0b970dfd19bb8c" width=500>

React 코어 팀 출신인 Dan Abramov가 수학 지식 없이 AI만으로 John Conway가 50년 전 제기한 [초현실수(surreal number)](https://en.wikipedia.org/wiki/Surreal_number) 관련 추측을 증명해 본 한 달간의 기록이다. 대상은 omnific integer에서 `ab = cd`이면 공통 세분(refinement)이 존재한다는 Conway의 refinement conjecture이며, 결과물은 증명 보조 도구 [Lean](https://lean-lang.org/)으로 작성한 증명이다. 저자는 아직 수학자의 독립 검증을 거치지 않았다고 밝히고 반례 제보를 요청한다.

과정은 실패의 연속이었다. 처음에는 모델에게 "돌파구를 찾으라"고 지시했지만, 그럴듯한 조어로 가득한 결과만 돌아왔다. 이후 Codex에서 PM, 수학, 반박(red), 자유 탐색, Lean 역할을 나눈 멀티 에이전트 "연구실"을 꾸렸지만 검증되지 않은 "논문"이 30편 가까이 쌓이며 무너졌다. 방향을 바꾼 계기는 참고 논문의 오탈자를 찾아 원저자에게 확인받은 일이다. 이것으로 모델과 Lean 결과를 어느 정도 믿을 근거를 얻었다. 그 뒤로는 전부 버리고 살릴 결과 하나만 남긴 채 다시 시작했다. 기존 논문을 형식화하는 Lean 에이전트와 새 결과를 형식화하는 Lean 에이전트를 별도 worktree로 분리했고, [Mathlib](https://github.com/leanprover-community/mathlib4)만 import하는 독립 명제 폴더를 두어 검토 범위를 줄였다.

회고에서 정리한 교훈은 에이전트 작업 전반에 통한다.

- 아이디어 탐색과 구체적 증명 작업을 분리하고, 수학 에이전트는 Lean보다 조금만 앞서게 한다
- 모델은 보이지 않는 것을 최적화하지 못하고, 보이는 것은 무시하지 못한다. 증명 구조를 Mermaid 다이어그램으로 보여 주고, 원하지 않는 용어는 코드에서 지운다
- 모델이 멋대로 만든 용어가 표류의 원인이었다. 분야에서 통용되는 용어로 강제하는 검사를 처음부터 뒀어야 했다
- 두 번의 "전부 버리고 다시 시작"이 프로젝트를 살렸다

토큰 사용량은 로그 기반 AI 추정으로 약 400억 토큰(출력 약 2억 1천만)이며, 현재 API 가격으로 환산한 전체 비용은 약 4만 달러라고 ChatGPT가 추정했다. Claude와 ChatGPT를 오가며 각 모델의 성향 차이를 관찰한 대목도 참고할 만하다.

## [The 5 Planes of Content Strategy](https://ozchen.com/5-planes-content-strategy/)

Oz Chen이 Jesse James Garrett의 책 [The Elements of User Experience](http://www.jjg.net/elements/)에 나오는 5단계 모델(Strategy, Scope, Structure, Skeleton, Surface)을 [콘텐츠 전략(content strategy)](https://en.wikipedia.org/wiki/Content_strategy) 관점에서 다시 읽은 글이다. 5단계 모델의 핵심은 각 단계가 아래 단계에 의존한다는 점이다. 저자는 이 모델이 구분한 "기능으로서의 제품"과 "정보로서의 제품" 가운데 콘텐츠 전략이 후자를 주로 맡는다고 본다.

단계별로 콘텐츠 전략가의 역할과 산출물을 정리한다.

- **Strategy**: 비즈니스 목표와 사용자 목표 정의. 사용자 분석, 경쟁 분석, 콘텐츠 브리프
- **Scope**: 기능 요구사항이 아닌 콘텐츠 요구사항 정의. 콘텐츠 인벤토리와 감사
- **Structure**: 정보 구조(IA) 설계. 사이트맵, 카드 소팅, 분류 체계와 메타데이터
- **Skeleton**: 인터페이스, 내비게이션, 정보 디자인. 콘텐츠 레이아웃, 와이어프레임, 메뉴 레이블
- **Surface**: 사용자가 실제로 접하는 표현. 인터페이스 문구, 스타일과 보이스 가이드, 타이포그래피

저자는 UX 디자인이 프로덕트 디자인으로 넓어지면서 콘텐츠 전략가가 정보 구조를 이어받을 기회가 생겼다고 주장한다. 디자이너, 콘텐츠 담당자와 역할 경계를 논의할 때 공통 틀로 참고할 수 있다.

## [AG-UI for product managers](https://x.com/samjulien/status/2104589165757370596)

<img src="https://pbs.twimg.com/media/HTLMQ3hagAA2RRK.jpg" width=500>

에이전트와 사용자 애플리케이션을 연결하는 오픈 프로토콜 [AG-UI(Agent-User Interaction Protocol)](https://github.com/ag-ui-protocol/ag-ui)를 만든 [CopilotKit](https://www.copilotkit.ai/)의 제품 책임자 Sam Julien이 PM 관점에서 AG-UI를 설명한 글이다. "어시스턴트를 추가하자" 같은 요구사항은 에이전트가 언제 승인을 받아야 하는지, 작업 도중 사용자가 마음을 바꾸면 어떻게 되는지를 정하지 않는다. 저자는 AG-UI가 이런 사람과 에이전트의 협업 방식을 설계하는 구체적인 어휘가 된다고 본다. [MCP](https://modelcontextprotocol.io/)가 에이전트와 도구를, [A2A](https://a2a-protocol.org/)가 에이전트끼리를 연결한다면 AG-UI는 에이전트와 사람이 쓰는 애플리케이션을 연결한다.

AG-UI는 응답 스트리밍, 도구 호출, 공유 상태 변경, 오류 같은 이벤트로 통신 구조를 정의하고, 프런트엔드는 이 이벤트로 진행 표시, 캘린더, 검토 폼 등을 그린다. 일정 변경 에이전트를 예로 들어 팀이 함께 정해야 할 다섯 가지 결정을 제시한다.

- **에이전트가 아는 맥락**: 선택한 일정이나 적용한 필터처럼 화면 상태 중 무엇을 공유 상태로 넘길지
- **작업 중 화면**: 스트리밍 메시지와 수명 주기 이벤트 중 어떤 진행 상황을 보여 줄지, 일부 서비스가 실패하면 무엇을 안내할지
- **응답 방식**: 문장 입력과 날짜 선택기 같은 인터랙티브 컴포넌트 중 어느 쪽이 결정을 더 쉽게 만드는지
- **사용자 개입 시점**: 사람의 입력을 요청하는 도구로 승인 단계를 두고, 승인 후 시간이나 요금이 바뀌면 다시 승인을 받을지
- **에이전트가 할 수 있는 일**: 화면 전환 같은 프런트엔드 도구와 예약 저장 같은 백엔드 도구의 범위, 사전 조건, 실패 동작. 권한과 비즈니스 규칙은 여전히 애플리케이션이 강제한다

저자는 도구 호출이 성공해도 제품 결과는 틀릴 수 있다고 강조한다. 사용자는 목요일을 골랐는데 에이전트가 화요일로 예약하고 성공을 보고하는 경우다. 사용자 행동, 에이전트 행동, 애플리케이션 변경의 흐름을 기록해 이런 실패를 평가 테스트로 바꾸자고 제안한다. "저장된 일정은 사용자가 승인한 시간과 일치해야 한다" 같은 수용 기준은 인터페이스, 에이전트 워크플로, 테스트를 함께 이끌 만큼 구체적이다. 에이전트 기능의 UI 요구사항을 기획자, 디자이너와 함께 정리해야 하는 FE 개발자에게도 참고가 된다. 공유 상태와 사람 개입(human-in-the-loop) 예제는 [CopilotKit Showcase](https://dojo.showcase.copilotkit.ai/)에서 확인할 수 있다.

## [토스 FE 개발자들의 검증법](https://www.youtube.com/watch?v=YCNcTpcDRf8)

<img src="https://i.ytimg.com/vi/YCNcTpcDRf8/maxresdefault.jpg" width=500>

2026년 8월 25일 열린 토스 웨비나 'AI 시대, 토스 FE는 어떻게 일할까'에서 AI로 만든 결과물을 어떻게 검증하는지 다룬 세션을 편집한 영상이다. 발표는 토스 FE 개발자가 AI를 더 잘 쓰도록 워크플로를 연구하는 2인 플랫폼 조직인 Front AI 팀이 맡았다. AI 도입 후 산출량은 크게 늘었지만 직접 쓰지 않은 코드를 이해하고 믿기까지 걸리는 시간이 오히려 늘었다는 문제의식에서 출발해, 실제 기기에서 돌아가는 E2E 테스트에 집중하게 된 과정을 소개한다.

처음에는 PRD와 구현이 모두 코드에 있다고 보고 코드에서 화면 흐름과 시나리오를 추론해 E2E 테스트를 자동 생성하려 했지만 실패했다. 검증하려는 사람의 의도는 코드에 드러나지 않는다는 이유였다. 이후 서비스 개발자를 직접 만나 보니 E2E가 필요 없어서가 아니라 만들 수 없어서 수작업으로 검증하고 있었다. 팀은 얼굴 인식 결제, 토스쇼핑처럼 실수 한 번의 비용이 큰 영역에 들어가 테스트를 직접 작성하면서 인증 API, 테스트용 상품 검색 노출처럼 테스트를 막던 요소를 해결하는 도구를 하나씩 만들었다. 사내 디바이스 팜을 API로 조작하는 도구를 에이전트에 제공하고, ELK에 쌓인 액션 로그를 Elasticsearch MCP로 조회하는 스킬도 만들었다. 테스트 작성은 자연어로 에이전트에게 시작 지점을 지시하고, 에이전트가 못 하는 조작은 사람이 직접 눌러 보여 주면 이를 모아 테스트 코드를 생성하는 방식이다.

깨지지 않는 테스트를 위해서는 실패 시 디바이스 팜 녹화 영상, 기기 로그, API 호출 기록(JSONL)을 저장하는 replay 도구를 만들었다. 원래 사람이 CI 실패 원인을 쉽게 파악하도록 만든 도구였지만, 이를 그대로 에이전트에 넘기자 버튼 문구 변경 같은 실패를 스스로 고칠 수 있었다고 한다. 사람을 위한 도구를 만들어 AI에 넘기는 것이 효과적이었다는 경험과, 기술보다 사용자의 실제 요구를 먼저 보라는 조언은 AI 검증 체계를 고민하는 FE 팀이 참고할 만하다. 전체 웨비나는 [다시보기](https://www.youtube.com/watch?v=xDVbTlFfu30)에서 볼 수 있다.

## [State of Devs 2026](https://2026.stateofdevs.com/en-US/)

<img src="https://assets.devographics.com/surveys/devs2026-og.png" width=500>

기술 스택이 아닌 개발자의 커리어, 직장, 건강, 가치관을 묻는 연례 설문 State of Devs의 2026년 결과가 공개됐다.

2026년 7월 5일부터 9월 5일까지 5,463명이 응답했으며, 개요는 [Software Stewardship Lab](https://stewardshiplab.org/)의 Miranda Heath가 작성했다. 올해는 처음으로 개발자의 정신 상태와 AI에 대한 인식을 묻는 문항이 추가됐다.

개요의 첫 문장은 "개발자로 살기에 불확실한 시기"다. 경력 중 겪은 직장 문제로 고용 불안(2,578명)과 낮은 임금(2,452명)을 꼽은 응답자가 각각 절반 가까이 됐고, 약 4분의 1은 5년 안에 본인 의사와 무관하게 직업을 바꿔야 할 가능성이 높다고 답했다. 최근 겪은 상태로는 일에 대한 의욕 저하(2,943명)와 업계에 대한 냉소(2,700명)가 가장 많았는데, 이는 [번아웃(burnout)](https://en.wikipedia.org/wiki/Occupational_burnout)의 징후와 겹친다. 경력 중 번아웃을 겪었다는 응답은 62%로 지난해와 같았다.

AI에 대한 시각은 긍정 49%, 부정 42%로 크게 갈렸고, AI 도구가 정신 상태에 긍정적이었다는 데 동의하지 않는 응답이 절반에 가까웠다. 1,500명이 넘는 응답자가 AI에 대한 서술형 의견을 남겼으며, AI를 안전하고 합리적으로 쓰는 방법, 일의 보람이 줄어드는 문제, 경영진의 과도한 생산성 기대가 자주 언급됐다. 기술 업계에 대한 감정으로는 지침(Exhausted), 환멸(Disillusioned), 호기심(Curious) 순으로 응답이 많았다. 결과 페이지는 성별 같은 조건으로 응답을 나눠 볼 수 있는 쿼리 빌더와 원본 데이터 다운로드를 제공하며, AI 도입 이후 개발자가 일을 어떻게 느끼는지 실측 데이터로 확인할 수 있는 자료다.

## [Full Course: Spec-Driven Development with Coding Agents](https://www.youtube.com/watch?v=hy8UstR2NEg)

<img src="https://i.ytimg.com/vi/hy8UstR2NEg/maxresdefault.jpg" width=500>

DeepLearning.AI가 JetBrains와 함께 만든 [명세 주도 개발(Spec-Driven Development, SDD) 강좌](https://www.deeplearning.ai/short-courses/spec-driven-development-with-coding-agents/)의 전체 영상이다. JetBrains 개발자 애드버킷 Paul Everitt가 강의하며, 바이브 코딩 대신 마크다운 명세를 먼저 쓰고 코딩 에이전트가 그 명세를 구현하게 하는 흐름을 한 시간 분량으로 보여 준다. 실습은 WebStorm과 Claude Code로 Next.js, React 기반 예제 앱 "Agent Clinic"을 만드는 방식으로 진행한다.

작업 흐름은 두 단계로 나뉜다.

- **프로젝트 헌장(constitution)**: 에이전트와 대화하며 `mission.md`(목적, 대상 사용자), `techstack.md`(기술 스택과 제약), `roadmap.md`(작은 단위로 나눈 기능 순서)를 `specs` 디렉터리에 작성한다.
- **기능 단위 반복**: 기능마다 별도 브랜치에서 계획, 요구사항, 검증 기준을 담은 명세를 만들고 커밋한 뒤, 컨텍스트를 비우고(`/clear`) 구현을 맡긴다. 리뷰에서 발견한 문제는 코드와 명세를 함께 고치도록 에이전트에 요청하고, 기능 사이에는 헌장과 로드맵을 다시 점검하는 재계획 단계를 둔다.

후반부에서는 기존 코드베이스(brownfield)에서 README와 TODO 파일로부터 헌장을 역으로 만드는 방법, 반복되는 요청을 에이전트 스킬로 묶는 방법, CLI 기반 스킬로 제공되는 [Context7](https://context7.com) 사용법을 다룬다. [Spec Kit](https://github.com/github/spec-kit), [OpenSpec](https://github.com/Fission-AI/OpenSpec) 같은 공개 SDD 도구와, 에디터와 에이전트를 연결하는 [Agent Client Protocol(ACP)](https://agentclientprotocol.com)을 이용해 에이전트나 IDE를 바꿔도 같은 흐름을 유지하는 방법도 소개한다. 코딩 에이전트를 팀 프로젝트에 들이면서 결과물의 일관성을 고민하는 개발자에게 도움이 되는 강의다.

## [Using AI for UX Work: Study Guide](https://www.nngroup.com/articles/ai-work-study-guide/)

<img src="https://media.nngroup.com/media/articles/opengraph_images/UX_-Study-Guide-1_1.png" width=500>

Nielsen Norman Group이 UX 업무에 AI를 활용하는 방법을 다룬 자사 아티클, 영상, 팟캐스트를 주제별로 묶은 학습 가이드다. AI를 써야 하는가에 대한 답은 "그렇다"이지만, 더 좋은 결과를 보장하지는 않으므로 비판적으로 판단하라는 입장을 전제로 한다.

자료는 AI를 기존 워크플로에 통합하는 법, 커리어와 역할 변화, 디자인, 리서치, 글쓰기, 서비스 디자인, 아이디어 발상과 워크숍, AI의 UX 영향 현황으로 나뉜다. 디자인 영역에서는 픽셀을 다루는 UI 작업보다 사용자 요구를 정의하고 AI에 줄 맥락을 정리하는 일이 중요해진다고 보고, AI로 와이어프레임의 충실도를 높이는 Promptframes, 막연한 프롬프트 대신 시각 키워드와 목업 데이터, 코드 조각을 주라는 AI 프로토타이핑 가이드 등을 소개한다. 리서치 영역에서는 합성 사용자(synthetic user)나 AI 진행 인터뷰가 실제 사용자 조사를 대체하지 못한다는 점을 반복해 강조한다.

현황 절의 자료는 발행 연도가 함께 표기되어 있어 시점에 따라 달라진 평가를 구분해 읽을 수 있다. 디자이너, 리서처와 AI 도입을 논의하는 FE 개발자에게 공통 참고 자료로 쓸 만하다.

## [AI Engineering from Scratch](https://aiengineeringfromscratch.com/)

<img src="https://aiengineeringfromscratch.com/og-image.png?v=4" width=500>

프레임워크를 쓰기 전에 AI 시스템의 구성 요소를 직접 구현해 보는 무료 오픈소스 커리큘럼이다. 선형대수부터 자율 에이전트까지 20개 단계, 523개 레슨으로 구성되어 있고, 예제 코드는 개념에 맞춰 Python, TypeScript, Rust, Julia 중 하나로 제공한다.

[역전파(backpropagation)](https://en.wikipedia.org/wiki/Backpropagation), 토크나이저, 어텐션, 에이전트 루프를 먼저 수식에서 출발해 손으로 구현하고, PyTorch 같은 프레임워크는 그 뒤에 등장한다. 레슨은 문제 읽기, 수식 유도, 코드 작성, 테스트 실행, 결과물 보관의 순서로 진행한다. 전체 단계와 별도로 AI 애플리케이션 구축과 배포, 소프트웨어 엔지니어링 기초, 에이전트 보조 엔지니어링, 제품 판단과 전달의 네 가지 핵심 학습 경로와 MCP, 에이전트 스킬 같은 집중 경로도 제공한다. 레슨을 묶은 EPUB, PDF 책도 GitHub 릴리스마다 함께 배포한다.

```bash
npx skills add rohitg00/ai-engineering-from-scratch   # 에이전트용 튜터 스킬 설치
git clone https://github.com/rohitg00/ai-engineering-from-scratch.git
```

튜터 스킬을 설치한 에이전트에서 `start-learning`을 실행하면 수준 진단 퀴즈를 거쳐 맞춤 경로에 따라 터미널에서 대화형으로 레슨을 진행한다. 가입이나 결제 없이 로컬에서 실행할 수 있어, LLM 기반 기능을 만들면서 내부 동작을 제대로 이해하고 싶은 FE 개발자가 참고할 만하다. [저장소](https://github.com/rohitg00/ai-engineering-from-scratch)는 MIT 라이선스다.

## [Commit. Keep moving.](https://oss.delino.io/async-commit-hook/)

Delino가 공개한 async-commit-hook(실행 파일명 `ach`)은 커밋 직후 테스트와 린트 같은 검사를 백그라운드에서 돌려 주는 로컬 도구다. 기존 [Git 훅](https://git-scm.com/docs/githooks)처럼 커밋을 붙잡아 두지 않고, 커밋된 소스의 격리된 사본에서 검사를 실행한 뒤 결과를 영수증(receipt) 형태로 남긴다. 결과는 `ach ui`가 띄우는 로컬 웹 UI(기본 `http://127.0.0.1:46309/`)에서 확인하며, 계정이나 별도 서버가 필요 없다.

검사 항목은 저장소의 `.config/async-commit-hook.toml`에 선언하고 함께 커밋한다. 검사마다 `command`, `depends_on`, `os`, `shell`, `optional`을 지정할 수 있고, 기본은 병렬 실행이며 `policy`로 `queue`(직렬화)나 `replace`(이전 검사 취소)를 고를 수 있다. JUnit, `go test -json` 리포트를 연결하면 종료 코드가 0이어도 리포트의 실패를 실패로 판정한다.

```bash
ach init            # 저장소 등록, post-commit 훅 설치
ach check --commit <sha> --json   # 최종 커밋의 검사 통과 여부 확인
ach hooks install --pre-push      # 선택: 검증 안 된 커밋의 push 차단
```

코딩 에이전트와 함께 쓰는 것을 염두에 둔 설계다. `ach agent install --client claude-code`처럼 Codex, Claude Code, OpenCode용 스킬과 [MCP](https://modelcontextprotocol.io/) 서버를 설치할 수 있고, 에이전트는 `ach_status`, `ach_failures`, `ach_rerun` 같은 도구로 결과를 확인하면서 다른 작업을 이어 간다. 이미 훅이 있으면 덮어쓰지 않고 수동 통합 명령을 출력하며, [Lefthook](https://github.com/evilmartians/lefthook) 연동 예시도 제공한다. 다만 문서에 따르면 첫 릴리스는 아직 공개되지 않은 상태다. [delinoio/oss](https://github.com/delinoio/oss) 모노레포에 포함된 Apache-2.0 라이선스 프로젝트다.

## [SoL-Pi](https://github.com/NVlabs/SoL-Pi)

<img src="https://nvlabs.github.io/SoL-Pi/assets/og.png" width=500>

NVIDIA 연구진이 자동 연구 루프(auto-research loop)로 찾아낸 효율화 기법을 묶은 코딩 에이전트 [Pi](https://github.com/earendil-works/pi)용 확장이다.

에이전트가 스스로 하네스 개선안을 제안하고 검증하는 루프에 152개 아이디어를 넣었고, 최종적으로 네 가지 기법이 남았다.

- **Action Fusion**: 파일 편집이나 쓰기와 뒤따르는 검증 명령을 한 번의 도구 호출로 실행한다.
- **ObservationPack**: 반복되는 큰 도구 결과를 핸들로 바꾸고, 필요할 때 원문을 페이지 단위로 다시 불러온다.
- **Evidence-Preserving Reducer**: 긴 진단 로그를 요약본으로 줄이되, 요약에 남긴 인용이 원본과 모두 일치할 때만 대체한다.
- **Online Context Compact**: 완료된 계획 단계를 Pi 기본 압축(compaction)의 후보 지점으로 삼는다.

Pi 소스를 수정하지 않고 공개 확장 API만 사용하며, 모든 기법은 기본값이 꺼져 있어 `sol-pi.json`에서 하나씩 켜는 방식이다. 연구진이 51개 장기 과제로 구성한 EdgeBench에서 측정한 결과, 원본 Pi 대비 평균 점수의 약 94%를 유지하면서 토큰 사용량을 45\~49% 줄였고 비용은 약 3분의 1 낮아졌다.

```bash
npm install --global @earendil-works/pi-coding-agent@0.85.1
pi install git:github.com/NVlabs/SoL-Pi
```

Node.js 22.19 이상이 필요하다. 자세한 방법론은 [블로그](https://nvlabs.github.io/SoL-Pi/)와 [논문](https://arxiv.org/abs/2609.20519)에 정리되어 있다. 에이전트 하네스의 토큰 비용이 어디서 새는지 궁금한 개발자가 읽어 볼 만한 MIT 라이선스 프로젝트다.

## [kubernetes3d](https://kubernetes3d.com/rack)

Kubernetes 클러스터를 [모듈러 신시사이저](https://en.wikipedia.org/wiki/Modular_synthesizer) 랙처럼 보여 주는 웹 인터페이스다. [Teenage Engineering](https://teenage.engineering/) 기기를 닮은 [스큐어모피즘](https://en.wikipedia.org/wiki/Skeuomorph) 디자인으로, 화면의 Pod, 노드, Deployment, Service, 이벤트는 녹화 영상이 아니라 실제로 동작하는 시뮬레이터 상태다.

비유는 오디오 장비에서 가져왔다. 이미지는 테이프, Pod는 그 테이프를 재생하는 데크, replica는 랙에 꽂힌 데크 수, Service는 엔드포인트를 채널로 가진 믹서다. replica 노브를 돌리면 ReplicaSet 크기가 실제로 바뀌고, 롤아웃은 `maxUnavailable` 설정을 지키며, 트래픽 생성기로 보낸 요청은 준비된 엔드포인트에 라운드 로빈으로 분배된다. 같은 클러스터를 랙이 노드, 서버가 Pod인 [서버실](https://kubernetes3d.com/) 화면으로도 볼 수 있다.

클러스터는 ngrok이 만든 [webernetes](https://github.com/ngrok/webernetes) 위에서 돈다. 백엔드 서버 없이 브라우저 안에서 apiserver, 스케줄러, 컨트롤러를 실행하는 Kubernetes 시뮬레이터로, npm 패키지(`@ngrok/webernetes`)로 제공된다. 조명이 비친 패널과 노브의 질감은 광원을 정의하면 그림자와 하이라이트가 따라 계산되는 CSS 라이브러리 [ambientcss](https://github.com/kikkupico/ambientcss)로 표현했다. 브라우저만으로 인터랙티브 인프라 교육 콘텐츠를 만드는 방식과 물리 기반 CSS 표현을 함께 참고할 수 있는 사례다.

## [TypeSafe AI](https://typesafe.ai/)

<img src="https://framerusercontent.com/images/RtIGTDwO43jR4ZDilesXiR5znc.jpg" width=500>

TypeSafe AI는 문자열을 생성하는 LLM 대신, 소프트웨어가 바로 쓸 수 있는 타입이 정해진 결정값을 반환하는 "System One 모델"을 만드는 AI 연구소다. 첫 공개 모델 Jev가 얼리 액세스로 제공된다. 창업자 Diogo Almeida는 OpenAI에서 ChatGPT의 기반이 된 지시 수행 연구에 참여했던 인물로, [사람 피드백 기반 강화학습(RLHF)](https://en.wikipedia.org/wiki/Reinforcement_learning_from_human_feedback)이 과신과 낮은 신뢰성 때문에 사람의 검토를 전제로 한다고 지적한다.

[문서](https://docs.typesafe.ai/introduction)에 따르면 API는 상태(state) 텍스트와 질문 목록을 받아 세 가지 질문 유형으로 답한다. 목록에서 하나를 고르는 Choice, 기준에 따라 점수를 매기는 Score, 참일 확률(0\~1)을 돌려주는 Noul이다. 모든 질문은 한 번의 호출 안에서 병렬로 따로 평가되고, Choice와 Score는 확률 분포와 신뢰도(confidence)를 함께 반환한다. TypeSafe는 자체 워크플로 평가에서 LLM 대비 193.6배 빠르고 444.6배 저렴했다고 밝히며, 이 수치가 실제 환경 기준으로는 높은 편일 것이라는 단서도 붙였다. 입력 가격은 10억 토큰당 42달러이고 출력은 과금하지 않는다.

권장 사용법은 복잡한 판단을 작은 질문으로 쪼개 각각 묻고, 결과를 코드에서 가중치로 조합하는 방식이다. 신뢰도가 높을 때만 자동으로 처리하고 낮으면 사람에게 넘기는 식으로 분기 기준을 코드에 둘 수 있다. 분류, 라우팅, 추출처럼 손으로 짠 조건문으로는 다루기 어려운 판단을 저지연으로 처리해야 하는 기능에서 검토해 볼 수 있다.

## [LMQL](https://lmql.ai/)

ETH Zurich SRI Lab이 만든 LLM 상호작용용 프로그래밍 언어다. Python의 상위 집합으로, 프롬프트를 문자열 템플릿이 아니라 타입, 제약, 제어 흐름을 갖춘 프로그램으로 작성한다.

최상위 문자열이 곧 프롬프트이고, 그 안의 `[ANSWER]` 같은 템플릿 변수를 모델이 채운다. `where` 절로 길이, 종료 문구, 허용 값 목록, 데이터 타입 같은 제약을 걸면 런타임이 이를 토큰 마스크로 변환해 생성 도중에 강제한다. 루프와 조건문으로 여러 단계의 프롬프트를 구성할 수 있고, 디코딩 방식도 `argmax`, `sample`, `beam`, `best_k` 중에서 고를 수 있다.

```python
"Q: What is the answer to life, the universe and everything?"
"A: [ANSWER]" where len(ANSWER) < 120 and STOPS_AT(ANSWER, ".")
"The answer is [NUM: int]"
```

백엔드는 OpenAI, Azure, 🤗 Transformers, llama.cpp를 지원하고 한 줄 수정으로 바꿀 수 있다. `pip install lmql`로 설치하며, 브라우저에서 바로 실행해 보는 [Playground](https://lmql.ai/playground/)도 제공한다. LLM 출력 형식을 프롬프트 문구가 아니라 언어 수준의 제약으로 통제하는 접근을 살펴보고 싶을 때 참고할 만한 Apache-2.0 라이선스 프로젝트다.

AiKA(AI Knowledge Assistant)는 [Backstage](https://backstage.io/) 기반 관리형 개발자 포털인 [Spotify Portal for Backstage](https://backstage.spotify.com/docs/portal/index)에 포함된 AI 에이전트다. 사내 문서와 서비스 정보를 대화형으로 조회하고, 여러 단계로 나눠 계획하고 실행하는 방식으로 질문에 답한다. 원문은 이 기능이 아직 개발 단계라고 밝히고 있다.

AiKA는 Portal의 [MCP](https://modelcontextprotocol.io/) 도구로 [소프트웨어 카탈로그](https://backstage.io/docs/features/software-catalog/), 검색, 플러그인 기능에 접근한다. 지식 소스는 Backstage Search가 색인한 대상이면 추가할 수 있으며, 기본으로 [TechDocs](https://backstage.io/docs/features/techdocs/), Confluence, 소프트웨어 카탈로그를 지원한다. 모델은 [AI Gateway](https://backstage.spotify.com/docs/portal/core-features-and-plugins/ai-gateway/index)에 설정한 `ai.models.languageModel`을 쓰고, AiKA만 다른 모델을 쓰려면 별도로 지정한다.

```yaml
aika:
  knowledgeTypes:
    - techdocs
    - confluence
    - software-catalog
  models:
    language: openai|gpt-5.4 # AI Gateway 기본 모델 대신 사용
```

사용할 모델과 제공자를 조직이 직접 고를 수 있어 데이터가 어디로 흐르는지 통제할 수 있다는 점을 장점으로 내세운다. Backstage로 내부 개발자 포털을 운영하는 조직이라면 문서 검색을 AI 에이전트로 확장하는 방식의 한 예로 참고할 수 있다.

## [bend](https://github.com/bendlang/bend)

<img src="https://raw.githubusercontent.com/bendlang/bend/main/media/game_law_kept.gif" width=500>

AI가 작성한 코드가 정해 둔 규칙을 어기지 않았는지 증명으로 검사하는 프로그래밍 언어 [Bend](https://bend-lang.com/)의 두 번째 버전이다.

Python과 비슷한 문법에 [의존 타입(dependent type)](https://en.wikipedia.org/wiki/Dependent_type)을 더했다. 핵심은 `LAWS.bend` 파일이다. "모든 잔액의 합은 0이다", "`list_sort()`는 항상 오름차순을 반환한다" 같은 앱의 규칙을 법칙(law)으로 선언하면, 코드를 수정할 때마다 그 법칙이 지켜진다는 증명을 요구하고 컴파일러가 이를 검사한다. 증명이 통과하지 않으면 AI는 다시 수정해야 한다. README는 "승리는 불가능하다"라는 법칙을 둔 게임에서 "보드 끝을 넘어가면 반대편으로 이어지게 해 줘"라는 요청을 받은 AI가 벽을 추가해 법칙을 지키는 예를 보여 준다.

```python
# LAWS.bend
law you_cant_win:
  for moves: List<Game.Move>
  board = Game.replay(Game.start(), moves)
  {Game.is_won(board) == False{} : Bool}
```

사용법은 설치 후 `AGENTS.md`에 `bend guide`로 언어를 익히고, 커밋 전에 `bend PROOF.bend`를 실행하라는 지시를 넣는 방식이다. 분할 정복 형태로 작성한 함수는 스레드나 락 없이 CPU 코어와 GPU로 병렬 실행되며, 컴파일 대상은 C, Metal, CUDA, JavaScript다.

```bash
curl -fsSL https://bend-lang.com/install.sh | sh
```

README의 제한 사항 목록에 따르면 Bend 1 프로그램은 호환되지 않고, JavaScript 대상은 단일 코어에서만 동작하며, HTTP, JSON, 정규식 라이브러리가 아직 없고, 컴파일러(커널 제외) 코드의 99%를 AI가 작성해 감사가 끝나지 않았다. 백엔드 용도로 Linux, macOS에서 쓰기를 권장한다. [웹사이트](https://bend-lang.com/#lab)에서 데모 코드를 고쳐 법칙을 깨 볼 수 있다. AI 코딩 에이전트의 결과물을 테스트 외의 방법으로 검증하는 접근이 궁금한 개발자가 살펴볼 만한 Apache-2.0 라이선스 프로젝트다.

## [penpot](https://github.com/penpot/penpot)

<img src="https://github.com/user-attachments/assets/cce75ad6-f783-473f-8803-da9eb8255fef" width=500>

브라우저에서 쓰거나 직접 서버에 설치해 운영할 수 있는 오픈소스 디자인, 프로토타이핑 플랫폼이다.

Penpot은 디자인을 SVG, CSS, HTML, JSON 같은 개방형 표준으로 표현한다. Inspect 탭에서 선택한 요소의 SVG, CSS, HTML 코드를 바로 확인할 수 있고, [CSS Grid와 Flex 레이아웃](https://help.penpot.app/user-guide/designing/flexible-layouts/)을 디자인 도구에서 그대로 지원해 반응형 화면을 코드와 같은 방식으로 구성한다. 디자인 토큰, 컴포넌트, 베리언트를 기본 기능으로 제공하며, 플러그인 시스템, 웹훅, 액세스 토큰 기반 API로 개발 도구와 연동할 수 있다.

최근에는 [MCP 서버](https://help.penpot.app/mcp/)로 AI 에이전트와의 연동을 강화하고 있다. Penpot 안에서 동작하는 MCP 플러그인이 현재 열린 페이지를 MCP 서버에 연결하고, Cursor나 Claude Code 같은 클라이언트가 이 서버를 통해 컴포넌트, 스타일, 토큰, 레이어 구조를 읽고 수정한다. 문서는 페이지 레이아웃에서 HTML/CSS 생성, 토큰을 코드 변수로 변환, 사용 중인 아이콘만 내보내기 같은 개발 작업 예시를 소개한다. 원격 서버와 로컬 서버 두 가지 방식을 지원하며, 2026년 10월 1일 2.18.1이 릴리스되었다.

Docker, Kubernetes 등으로 [셀프 호스팅](https://penpot.app/self-host)이 가능해 디자인 데이터를 사내에 두어야 하는 조직에서 검토해 볼 만하다. 디자인 시스템을 코드와 같은 기준으로 관리하고 싶은 FE 개발자가 살펴볼 만한 MPL-2.0 라이선스 프로젝트다.

## [Agentlas-OS](https://github.com/agentlas-ai/Agentlas-OS/)

<img src="https://raw.githubusercontent.com/agentlas-ai/Agentlas-OS/main/assets/readme/feature-wall/workflow-make-group-v2.gif" width=500>

작업 하나마다 전문 에이전트 팀을 꾸려 실행하는 에이전트 오케스트레이션 엔진이다. Claude Code, Codex, Cursor, Gemini 같은 에이전트 호스트 안에서 플러그인 형태로 동작한다.

동작은 세 단계로 나뉜다. 먼저 요청 문장을 역할, 인계 순서, 각 역할이 만들어야 할 결과물로 이루어진 작업 목록으로 분해한다. 이때 리뷰 단계가 앞선 작업을 다시 가리키는 순환 구조는 실행 전에 거부된다. 다음으로 로컬, 개인 클라우드, 공개 [Agentlas Hub](https://agentlas.cloud/hub)에서 작업별 후보 에이전트를 찾는데, 후보 목록에 순위를 매기지 않고 사용자가 쓰는 모델이 직접 고르며 선택 이유를 기록한다. 마지막으로 계획, 작업, 종합, 검증을 별도 호출로 실행하고, 독립 검증자가 통과시켜야 완료로 처리한다. 에이전트 카드는 [A2A](https://a2a-protocol.org/) v1.0 규격의 `/.well-known/agent-card.json`을 따른다.

```bash
curl -fsSL https://raw.githubusercontent.com/agentlas-ai/Agentlas-OS/main/scripts/install-all-runtimes.sh | bash
hephaestus doctor   # 연결된 호스트와 누락된 설정 확인
```

설치 스크립트는 `$HOME` 밖에는 아무것도 쓰지 않지만, `PATH`에서 찾은 지원 호스트 전부에 플러그인과 MCP 설정을 등록한다. README에 쓰기 대상 경로 목록이 있으니 설치 전에 확인하는 것이 좋다. GUI가 필요하면 같은 런타임을 쓰는 Agentlas Desktop도 제공한다. 여러 에이전트에게 작업을 나누어 맡기는 구조를 설계할 때 참고할 만한 Apache-2.0 라이선스 프로젝트다.
